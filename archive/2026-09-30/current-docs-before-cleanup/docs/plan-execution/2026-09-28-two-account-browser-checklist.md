신규 가입은 원래 확인 요청부터 10분 안에 마쳐야 한다. 입력 단계에서 만료 안내가 나오면 사용자가 준비된 뒤 새 확인 요청·링크 처리를 이어간다. 현재는 두 창의 비밀번호·닉네임 직접 설정을 [기존 질문 HTML](2026-09-28-release-blockers-questions.html)로 안내한다. 가입 메일 한 통 완주·재설정·registered/pending 분기와 후속 앱 과업은 아직 미완료다.

아래는 실제 발송 전의 과거 보고와 절차다. 최신 상태는 위 표를 따른다.

**2026-09-29 안내 정정:** 이번 QA Chrome 재개 과정에서 AI는 실제 A·B 주소로 메일 발송을 실행하지 않았다. 발송된 메일이 있는 것처럼 스팸함 확인을 요청한 안내는 잘못이었다. 사용자의 “스팸함으로 갔을 것”이라는 추정은 발송·수신 증거가 아니다. 최신 Preview의 소유 확인 요청은 기존 가입 여부를 미리 판별하지 않고 확인 메일을 발송하도록 구현돼 있으며, 링크 사용 뒤 가입 상태를 구분한다. 실제 요청·발송 결과를 먼저 확인한 뒤 메일 수신 시험을 진행한다.

사용자는 시험용 메일함 두 개를 준비했고 브라우저 로그인·인증을 직접 할 수 있다고 확인했다. 아래 네이버·구글 결과는 **사용자가 직접 본 메일·브라우저 결과**이며, A·B 계정 분리·한국어 문안·후속 앱 과업까지 검증했다는 뜻은 아니다. 메일 주소·비밀번호·링크 토큰·사연/대화 원문은 이 문서나 채팅에 적지 않는다. 계정은 A·B로만 구분한다.

| 사용자 보고 항목 | 네이버 | 구글 |
| --- | --- | --- |
| 메일 위치 | 받은편지함 | 스팸함 |
| 확인 링크·앱 로그인 연계 | 성공 | 성공 |
| 한국어 제목·본문·버튼 | 이번 보고에서 언급 없음 | 이번 보고에서 언급 없음 |

이미 가입한 주소로 가입을 다시 시도했을 때 메일은 오지 않았으나 기존 공개 화면이 발송된 것처럼 안내했다고 사용자가 보고했다. 로컬 화면은 **요청 접수·신규 가입 대상에만 메일 도착 가능**으로 고쳤다. 이는 실제 중복 판별이 아니며 새 화면은 아직 배포·브라우저 확인 전이다.

추가 [소유 확인 흐름](2026-09-28-duplicate-signup-decision.md)은 **Preview에서만** 기능 플래그를 켰다. 최신 시험 주소는 <https://thinkerbell-2mqa6zemo-jjackbb-projects.vercel.app/>다. 최신 배포의 `/api/health` 200과 앞선 배포의 가입 확인 API 잘못된 주소 400을 확인했지만 실제 메일은 제가 보내지 않았다. Preview는 Vercel 배포 보호 때문에 프로젝트 계정 로그인이 필요할 수 있다. 앞서 사용자가 A·B 가입 링크 시험을 완료했다고 선택지로 답한 기록은 있으나, **최신 Preview에서의 A·B 과업은 아직 시험하지 않았다고 후속 확인했다.** 따라서 계정별 메일 위치·한국어 문안·링크 후 로그인 상태와 아래 과업의 합격 판정은 보류한다. A의 **가입 완료**, B의 **새 주소**, 별도 미완료 계정의 **가입 확인 대기**를 메일 링크 사용 후에만 구분하고, 링크 재사용·만료·타인 주소 입력만으로 상태 조회 불가를 확인한다. 새 주소는 **소유 확인 메일 한 통만** 받는지, 링크 사용 후 비밀번호·닉네임 설정→로그인·새로고침 복원이 되는지 확인한다. 기존 계정은 재설정 메일 요청→복귀→새 비밀번호 저장→재로그인을 확인한다. 이메일 주소·링크 원문은 기록하지 않는다.

## 지금 공개 앱에서 가능한 인증 시험

현재 공개 주소는 <https://thinkerbell-eight.vercel.app/>이다. 2026-09-28 현재 공개 앱에는 검토 브랜치의 비공개·AI 횟수·도움 평가 기능이 배포되지 않았다. 따라서 아래 인증 확인만 먼저 수행한다.

1. 서로 다른 브라우저 프로필 또는 일반 창·시크릿 창에서 A와 B를 분리한다. 두 창이 같은 로그인 세션을 공유하지 않는지 확인한다.
2. A로 신규 회원가입 → 메일 수신 위치 확인 → 한국어 제목·본문 확인 → 확인 링크 클릭 → 앱 복귀 직후 로그인 상태 확인을 한다. 비밀번호나 링크는 공유하지 않는다.
3. B도 같은 순서로 확인한다. A 창이 B 계정으로 바뀌지 않는지 확인한다.
4. 실제 만료 링크는 의도적으로 기다려 시험할 경우에만 진행한다. 받은 링크 원문을 기록하지 않고, 오류 안내·재발송·새 링크 로그인 여부만 남긴다. 인증 메일의 중복 발송을 피한다.

## 새 DB 구조·Preview 배포 뒤에만 가능한 과업

운영 DB에는 `stories.visibility`, `ai_feedback`, `ai_quota_reservations`를 포함한 호환 구조가 적용됐고 위 Preview에는 비공개 화면을 켰다. 직접 쓰기 차단은 새 서버의 실제 검증 전이므로 아직 적용하지 않았다. A가 사연을 작성하고 B가 조회·투표·댓글·AI 방을 시험한다. A가 비공개로 바꾸면 A는 새 댓글을 **달지 못하고** 기존 댓글만 보며, B는 원문·댓글·새 방을 볼/만들 수 없어야 한다. B의 이미 소유한 AI 방은 남아야 한다. 다시 공개하면 원래 작성일과 기존 댓글·투표가 유지되어야 한다.

AI에서는 옛 방의 새 정상 저장 답변 뒤 평가, 새 방 첫 답변의 완료·저장 결과 분리, 저장 실패 후 입력 보존·새 답변 재요청, 실패 미차감, 전환 전 방의 무료 이어쓰기, 두 계정/두 탭의 하루 3회와 자정 경계를 구분해 기록한다. **최신 Preview는 시험용 2026-09-28 시작 시각과 서버 준비 플래그가 켜져 있다.** `/api/health` 200과 익명 `/api/ai/quota`의 `AUTH_REQUIRED`, [임시 계정의 포텐스 답변·저장·차감](2026-09-28-preview-integration-smoke.md)을 확인했다. [17:49 Preview의 계정 전환·Realtime 화면](2026-09-28-preview-browser-followup.md)과 [18:47 Preview의 저장 실패 주입·재요청·복원](2026-09-28-in-progress-release-preflight.md)도 임시 계정 범위다. 동의 뒤 이벤트가 QA 속성의 DebugView·처리 보고서에 실제 표시되는지, **사용자가 관리하는 A·B 메일 계정**의 앱 과업은 여전히 `NOT_RUN`이다.
