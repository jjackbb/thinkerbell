## Production 전환 읽기 전용 사전 점검

**2026-09-29 사용자 확인:** 사용자는 Production의 `SUPABASE_URL`·`VITE_SUPABASE_URL`을 추천값 `https://vzhyhadjtaqbapicjrco.supabase.co`로 다시 저장했다고 답했다. 재설정 여부는 더 이상 판단 대기가 아니다. 이는 사용자 설정 완료 보고이며 새 Production 배포의 실행 검증은 남아 있다. “크롬에서는 스팸메일함으로 갔을 것”이라는 답은 메일 서비스와 실제 수신 확인 여부가 불명확하므로 A·B 메일 시험 통과로 기록하지 않는다.

- Vercel `jjackbb-projects/thinkerbell`의 최신 Preview는 `Ready`; 공개 별칭 `thinkerbell-eight.vercel.app`은 여전히 2026-09-26 Production `dpl_9ZA4RF2b6Lajs5LFmdefQ5WFyCdq`를 가리킨다. 공개 HTML의 JS 번들에는 니편내편 Supabase ref가 있지만 새 AI 횟수 코드와 GA4 로더는 없다. 서버가 사용하는 실제 URL 값은 이 검사로 확인할 수 없다.
- 후속 재조회에서 공개 JS 번들의 `VITE_SUPABASE_URL` 프로젝트 ref가 `vzhyhadjtaqbapicjrco`와 일치했다. 사용자는 `APP_URL`이 공개 주소와 일치한다고 확인했다. 이 둘은 **현재 공개 배포의 클라이언트 번들**과 **사용자 설정 확인**이며, 다음 Production 배포 변수의 실제 값이나 서버용 `SUPABASE_URL` 값까지 증명하지 않는다.

Vercel 공식 읽기 API에서도 `APP_URL`, `SUPABASE_URL`, `VITE_SUPABASE_URL` 세 변수의 `production` 대상과 `sensitive` 형식을 확인했다. 각 변수의 개별 조회는 HTTP 200이지만 `decrypted=false`이고 값이 없었다. Sensitive 값은 저장 후 읽을 수 없으므로 URL 값 일치 여부는 판정할 수 없다. 처음의 형식 불일치 판정은 **마스킹에 의한 거짓 경고**로 취소한다. 토큰·비밀값은 기록하지 않았고 임시 파일은 지웠다.
- DB의 호환 마이그레이션 9건은 적용 이력에 남아 있고, 차단 대상 직접 `INSERT/UPDATE` 정책 7개의 이름·명령·역할은 [사연·댓글·AI 차단 SQL](2026-09-28-release-gates.md)의 사전 조건과 일치한다. SQL은 **실행하지 않았다**. 정리 cron 4개는 활성이다. 새 AI 보관·사연 접근 정리 두 작업은 아직 첫 실행 기록이 없다.

**현재 전환 중단 조건:** 사용자는 최신 Preview의 실제 메일 계정 A·B 과업이 **아직 미실행**이라고 밝혔다. QA 속성은 게스트 `story_view`의 Realtime 표시와 합성 `qa_debug_probe`의 DebugView 표시까지 확인했지만, 실제 AI 과업 이벤트는 미확인이다. 운영 AI 활성화 시각·Production 기능 변수는 정해지거나 적용되지 않았다. 처리 보고서는 공개 후 데이터가 쌓인 뒤 대조한다. 이 상태에서 새 Production 앱을 배포하면 `AI_QUOTA_ACTIVATES_AT` 부재로 서버 AI 요청이 `AI_QUOTA_NOT_READY`가 될 수 있다. 기존 공개 앱은 브라우저 직접 쓰기에 의존하므로 DB 차단 SQL을 먼저 실행하면 저장 경로가 끊긴다. 따라서 **Production 앱 배포·변수 활성화·직접 쓰기 차단은 미실행**이다.

**복구 시험 기준 확정:** 사용자는 이의 제기·AI 방 삭제에 실제 운영 장애를 일부러 일으키지 않고, 주입 오류 때 입력·확인 상태 보존과 주입 해제 뒤 실제 서버 재시도 성공을 첫 공개 전 판정으로 선택했다. 실제 장애를 재현했다는 뜻은 아니며, 발생하면 운영 기록으로 별도 검증한다.

전환 시에는 [기존 전환 순서](2026-09-28-release-gates.md)대로 실제 계정 과업 결과와 변수 대상·시각을 먼저 확정하고, Preview와 같은 서버 경로가 새 Production 배포에서 동작하는지 확인한 뒤 차단 SQL을 적용한다. 데이터 노출·저장 실패가 나오면 공개를 중단하고 이전 검증 배포로 되돌리되, DB 구조를 파괴적으로 되돌리거나 이용자 데이터를 지우지 않는다. 공개 후 GA4 기준선과 처리 보고서는 실제 이벤트가 쌓인 뒤 버전·기간을 붙여 대조한다.
