Supabase Site URL은 사용자가 공개 주소로 저장했고 따옴표가 없다고 확인했다. 사용자 확인으로 Custom SMTP에 Resend 발송 전용 키·발신 설정을 저장했고, 이후 Confirm Email을 켜 새 가입부터 앱 복귀까지 시험했다. 기존 계정은 변경하지 않기로 했다. 인증 화면만 커밋 `7b688e2`로 선배포해 공개 JS의 안내·재발송 코드 반영을 확인했다. 사용자가 합성 만료 링크 오류 화면을 확인했고, 니편내편 Auth 집계에서 신규 계정 1명의 생성·확인을 확인했다. 2026-09-26 조회 당시 Auth 사용자 46명 모두 확인 시각이 있었지만, 기존 45명의 과거 메일 소유권 검증 증거는 아니다. 네이버 받은편지함 수신과 앱 복귀 직후 로그인 상태도 사용자가 확인했다. 실제 만료 링크·재발송과 새 계정의 앱 과업은 별도 확인이 필요하다. [신규 가입 시험 기록](docs/plan-execution/2026-09-26-auth-email-verified.md). 영어로 온 가입 확인 메일을 사용자가 한국어 제목·본문으로 직접 수정했다고 알렸다. | 내 사연을 비공개로 변경 | 다른 모든 이용자의 목록에서 숨기고 작성자만 확인할 수 있는 공간으로 이동. 타인의 원문·댓글 조회와 신규 투표·댓글 차단. 공유 링크·직접 API 요청에도 동일하게 적용 |
| 비공개 후 재공개 | 기존 댓글·투표를 보관했다가 다시 표시. 재등록·재집계로 중복을 만들지 않음 |
| 비공개 중 새 댓글 | 작성자를 포함한 모든 이용자가 새 댓글을 달지 못함. 기존 댓글은 보관 후 재공개 시 다시 표시 |
| 비공개 사연의 작성자 | 자기 사연으로 새 AI 대화 생성 가능 |
| 비공개 사연의 다른 이용자 | 기존에 소유한 AI 대화는 계속 이용. 새 대화방 생성은 차단 |
| 기존 공감 대화의 관점 변경 | 보존된 사연 맥락으로 변경 가능. 비공개 원문을 다시 조회하지 않음 |
| 성인 판정 사연 | 첫 공개에서 신규 등록·공개 노출·관련 AI 이용 차단. 기존 자료는 임의 삭제하지 않음 |

비공개 안내에는 **이미 만들어진 다른 이용자의 AI 대화에 포함된 내용은 남을 수 있음**을 명시한다. 비공개를 기존 대화에서까지 내용을 지우는 기능으로 설명하지 않는다.

작성자 비공개 사연은 마이페이지 **‘작성한 사연’ 안에서 공개·비공개를 구분**해 확인한다. 다시 공개해도 원래 `createdAt`을 유지하므로 공개 목록에서 새 사연처럼 위로 올리지 않는다. 비공개 구현은 공개 조회 정책만 바꾸면 완료되지 않는다. 댓글 조회·쓰기, 투표·공감·신고 등 서버 함수, 실시간 화면 갱신, 새 AI 대화방 생성과 기존 대화 이어하기를 함께 확인한다. [접근 경계 점검](docs/plan-execution/2026-09-25-author-private-boundary.md)

기존 `isHidden=true` 사연 1건은 사용자의 요청에 따라 삭제 직전 ID·연결 기록을 재검증한 뒤 **해당 행만** 삭제했다. 새 개인 숨김이나 작성자 비공개로 이관하지 않았다. [삭제·검증 기록](docs/plan-execution/2026-09-25-story-hides-applied.md)

**가입·투표·AI 이용 규칙**

- 가입은 이메일 확인 후 완료한다. 실제 외부 주소로 인증 메일 발송, 재발송, 만료, 확인 후 앱 복귀까지 연결한다. 게스트의 공개 사연 둘러보기는 유지한다.
- 기존 가입 여부는 이메일 주소 입력만으로 보여주지 않는다. 해당 메일함의 소유 확인 링크를 사용한 뒤 가입 가능·가입 확인 미완료·가입 확인 완료를 구분해 안내한다. 새 가입의 확인 메일은 한 통이며, 비밀번호를 잊은 기존 이용자는 재설정 메일을 요청할 수 있다. [결정과 검증 범위](docs/plan-execution/2026-09-28-duplicate-signup-decision.md)
- 투표는 같은 선택 재클릭 무시, 반대쪽으로 한 번 변경, 취소 없음으로 유지한다. 본인 사연 투표 제한도 서버에서 확인한다.
- 댓글 공감은 로그인 계정당 댓글별 1회만 누를 수 있고, 다시 누르면 취소한다. 연타·재시도·기기 변경으로 숫자가 중복 증감하지 않게 서버에서 확인한다. 과거 계정별 기록 없이 남은 표시 숫자 31개는 사용자 결정에 따라 0으로 재설정했다.
- 남의 사연으로 새 AI 대화는 하루 3회, 한국 시간 기준으로 적용한다. 내 사연과 이미 정상 이용한 대화 이어하기는 추가 차감하지 않는다.
- 전환 시각 **이전에 만든 AI 대화방 7개는 모두 무료 이어하기**로 인정한다. 과거 자동 저장 이력만으로 정상 답변 여부를 추정해 다시 차감하지 않는다.
- 새 대화의 첫 요청 중에는 횟수를 예약하고, **첫 정상 답변이 완료되면 차감**한다. 실패·완료 전 취소는 예약을 반환한다. 실패한 방을 다시 열었다는 이유로 제한을 우회하지 못하게 한다.
- 화면에 AI 답변이 나왔어도 **DB 저장이 실패하면 차감하지 않는다**. 입력과 미저장 답변을 경고와 함께 화면에 남기고, 재시도는 새 AI 답변을 요청한다. 저장 완료 여부와 답변 완료 계측은 구분한다.
- **개인 숨김은 사연 노출에만 적용**한다. 그 사연에서 이미 소유한 AI 대화방은 AI 목록에서 계속 열 수 있으며, 별도 삭제는 이용자가 선택한다.
- 첫 공개에서는 AI 대화 내용을 자동 삭제하지 않는다. 이용자의 대화 삭제·계정 탈퇴 때만 삭제한다. 도움 평가의 최대 30일 보관은 별개다.
- 하루 3회의 귀속 날짜는 대화방을 연 날이 아니라 **첫 실제 AI 요청을 서버가 받은 한국 날짜**로 고정한다. 자정 후 답변이 완료돼도 성공한 요청은 그 날짜의 몫으로 확정한다. 횟수 예약·완료·반환 기록은 종료 후 30일 보관하며, 대화 본문·도움 평가의 보관 규칙과 구분한다.
- 콘텐츠 검사 실패는 안전 판정으로 처리하지 않는다. 입력을 보존하고 ‘다시 검사’로 실제 포텐스 API를 호출한다. 수정된 내용에는 다시 검사한다.

**구현에 필요한 인터페이스 변경**

| 영역 | 구현 계약 |
|---|---|
| 사연 생성·수정 | 서버에서 인증·작성 권한·콘텐츠 검사를 확인한 뒤 저장. 브라우저가 보낸 검사 결과만 신뢰하지 않음 |
| 공개 상태·개인 숨김 | 사연의 `public/private` 상태와 사용자별 숨김 관계를 분리. 개인 숨김은 사용자·사연 조합으로 중복 방지 |
| AI 대화 생성 | 사연 ID·모드·설정을 받아 서버가 접근 권한을 검사하고 소유 대화방과 당시 맥락을 저장 |
| AI 요청 | `/api/chat-stream`에 인증 토큰, 대화방 ID, 메시지, 중복 방지 식별자를 전달. 서버가 소유권·사용량·저장된 맥락을 확인 |
| AI 완료 | 스트림의 `delta / done / error`를 구분. 정상 답변 저장 후 완료 처리. 고정 인사·부분 응답·모의 응답을 정상 AI 완료로 세지 않음 |
| 도움 평가 | 대화 이용 구간별 평가 1건과 점수 1~5, 버전·모드·저장 시각·만료 시각 저장. 본인과 운영자만 접근 |
| 공통 실패 | 인증·권한·횟수·검사·공급자·저장 오류를 구분한 코드 반환. 원문 오류나 비밀키를 화면·GA4에 보내지 않음 |

서버에는 중복 요청 방지와 동시 요청 제한을 둔다. AI 하루 3회 규칙만으로 전체 API 호출이 제한됐다고 간주하지 않는다. 기존 대화·DB 구조는 실제 원격 상태와 비교한 뒤 호환 가능한 변경부터 적용한다.

## 3. 버튼 이벤트·GA4·도움 평가

**모든 노출 버튼에 기능 계약을 붙인다.** 기존 소스의 버튼 위치 153곳을 출발점으로, 실제 화면의 조건부·반복 요소를 대조해 최종 목록을 만든다.

2026-09-28 현재 TSX의 정적 `<button>` 선언 174곳에 고유한 `data-button-id`를 부여하고 [위치·ID 목록](docs/plan-execution/2026-09-28-button-inventory.md)으로 재집계했다. 실제 발송 기능이 없는 알림 토글 3개는 첫 공개의 “준비 중” 범위에 맞춰 제거했다. [핵심 버튼 계약](docs/plan-execution/2026-09-28-core-button-contract.md)과 [174개 화면별 계약 지도](docs/plan-execution/2026-09-28-button-behavior-matrix.md)에 선행 조건·성공·실패·이벤트·검증 케이스를 구분했고 ID 누락·중복 0개를 확인했다. 조건부·반복 실제 노출과 서버 결과·GA4 수신은 별도 시험이 남아 있다.

각 항목에는 다음을 기록한다.

`화면 / button_id / 동작 / 선행 조건 / 성공 결과 / 실패·취소 / 이벤트 / 검증 케이스`

버튼 문구를 바꿔도 같은 행동의 ID는 유지한다. 기능 검증 대상과 GA4 전송 대상은 구분하며, 민감한 위기 지원 행동 등은 외부 전송 제외 사유를 명시한다.

| 구분 | 이벤트와 발생 기준 |
|---|---|
| 화면·버튼 (첫 공개 GA4 제외) | `page_view`, `ui_click` — 기능 검증 후보. 수동 화면 이동·전체 클릭은 외부 전송하지 않음 |
| 작업 결과 | `operation_start / success / error` — 실제 요청과 서버 결과 |
| 실행 제한 | `action_blocked` — 로그인·권한·횟수 등으로 실행하지 못한 시도 |
| 사연·참여 | `story_view`, `story_publish_success`, `vote_submit`, `vote_change_success`, `comment_create_success` |
| AI 진입 | `ai_entry_click → ai_mode_select → ai_settings_confirm 또는 ai_start_select → ai_chat_open` |
| AI 이용 | **`ai_chat_turn1`을 대표 주요 이벤트로 지정**, `ai_chat_turn3`는 추가 이용 지표 |
| 마무리·평가 | `ai_chat_finish`, `ai_feedback_view`, `ai_feedback_submit` — 평가값은 GA4 제외 |

클릭을 성공으로 세지 않는다. 재시도·연타·화면 재렌더·계정 교체로 완료 이벤트가 중복되거나 누락되지 않게 한다. AI 1턴은 사용자의 메시지에 대한 정상 응답 한 쌍이며, 실패한 전송은 턴 수에 포함하지 않는다. 첫 공개 GA4는 위 핵심 과업의 진입·선택·실제 저장 결과만 보낸다. 가입·로그인·계정·신고·위기 지원 행동과 단순 화면 이동은 외부 전송하지 않는다.

**GA4 수집 방식**

- 이용자가 동의한 뒤 태그를 로드하는 기본 동의 방식으로 구현한다. 동의 전·거부 상태에서는 Google에 전송하지 않고 과거 행동을 소급 전송하지 않는다. 설정에서 선택을 변경할 수 있게 한다. [Google 동의 모드](https://developers.google.com/tag-platform/security/concepts/consent-mode)
- 선택적인 내부 행동 분석 로그도 동의 범위에 맞춘다. 기능 저장·인증·오류 처리에 필요한 기록은 목적을 구분해 안내한다.
- 사연·댓글·대화·신고 원문, 이메일·닉네임·계정 ID, 도움 평가값을 GA4로 보내지 않는다. URL·페이지 제목·오류 메시지도 정제한다.
- 첫 공개에서는 화면 전환의 수동 페이지뷰를 보내지 않는다. 앱의 임의 방문 ID로 GA4의 `session_id`를 덮어쓰지 않는다. 동의 뒤 Google 태그가 만드는 기본 세션 이벤트는 별개로 확인한다.
- `release_id`, 화면, 진입 위치, 모드, 신규·이어하기, 모집 경로, 오류 종류를 기준으로 분석한다. 내부 시험과 운영 데이터를 분리한다. 9월 30일 구현: `?source=community`와 `?source=sns`를 공유에 사용하며 지정하지 않은 값은 `unattributed`다. 별도 기술 시험은 `?source=qa` → `technical_test`로 구분한다. 쿼리 원문·임의 플랫폼 이름은 전송하지 않는다. 분석 동의 뒤에만 해당 범주를 탭 세션에 보관하고 동의 철회 시 지운다.
- `conversation_type=new`는 새 방 생성, `continuation`은 기존 방·서버 복구 방 재진입을 뜻한다. 단순히 과거 말풍선이 없다고 새 방으로 세지 않는다. `ai_chat_turn1`은 열린 대화 회차의 첫 정상 완료 답변이며 신규/이어하기를 나누어 분석한다. 서버의 명시적 답변 완료 신호와 비어 있지 않은 표시 내용을 확인해 집계한다. 이후 저장에 실패해도 답변 완료는 유지하고 저장 실패는 별도로 기록한다. `ai_chat_turn3`도 같은 완료 기준을 사용한다. 부분 응답·빈 응답·완료 신호 없는 종료는 세지 않는다. 횟수 차감과 도움 평가 가능 여부는 정상 저장을 기준으로 유지한다.
- GA4와 내부 이벤트 저장은 서로 기다리지 않는다. 분석 전송 실패가 제품 사용을 막지 않게 한다.

**확인할 지표**

| 질문 | 지표 |
|---|---|
| 사연을 본 사람이 AI까지 도달하는가? | 동의한 세션의 사연 조회 → 첫 정상 AI 답변 도달 비율 |
| 어디에서 막히는가? | AI 진입·모드 선택·설정·첫 요청 단계별 이탈과 오류 |
| 작성·참여 기능이 정상인가? | 유효 요청 대비 실제 저장 성공·실패, 중복 발생 |
| AI가 도움이 됐는가? | 유효한 1~5점 평가 중 4~5점 비율. 점수별 분포는 개인 평가 보관 기간 안에서만 확인하고 장기 집계에는 남기지 않음 |
| 평가가 일부 사람에게만 치우쳤는가? | 평가 대상·노출·제출·미응답 수와 비율 |
| 경험이 나빠지지는 않았는가? | 첫 답변 대기 시간, 응답·저장 실패, 도움 평가와 인터뷰의 부정적 반응 |

도움 문항은 **“이 AI 대화가 도움이 되었나요?”**로 한다. 선택지는 ‘전혀 도움 안 됨 / 별로 도움 안 됨 / 보통 / 조금 도움 됨 / 매우 도움 됨’이며 건너뛰기를 제공한다. **두 AI 모드 모두 정상 저장된 답변 1회 이상 뒤** ‘대화 마무리’를 누르면 평가를 보여준다. 전환 전 옛 방도 과거 말풍선만으로 평가를 열지 않고 **새 정상 저장 답변**을 받은 뒤 연다. 마무리는 대화를 보존하며 삭제는 별도 행동이다. 제출 성공을 확인하고 평가값은 GA4에 보내지 않는다.

개인별 평가는 최대 30일 보관하고 대화 삭제·탈퇴 시 함께 삭제한다. 이후에는 **월 단위·두 모드 합계에서 서로 다른 점수 응답자 최소 5명을 월말에 확인할 수 있는 경우만** 전체 유효 평가 수와 4~5점 수를 남긴다. 31일인 달의 초반 평가가 월말 전에 만료돼 응답자 수를 증명할 수 없으면, 실제로 5명 이상이었을 가능성이 있어도 그 달의 임시 합계를 버린다. 건너뛰기, 작은 집단, 일별·모드별·점수별 셀은 장기 보존하지 않는다. 이 방식의 호환 SQL은 격리 시험 후 운영 DB에 적용했고 구조·권한을 조회했다. 첫 일일 정리와 실제 월말 집계는 아직 확인하지 않았다. 미응답을 불만족으로 처리하거나 응답자 만족도를 전체 이용자의 만족도로 표현하지 않는다.

## 4. 검증과 실제 공개

| 단계 | 작업 | 다음 단계로 가는 기준 |
|---|---|---|
| 1. 환경 확인 | 실제 Vercel·Supabase 프로젝트, 원격 DB·권한·요금제, GA4 소유 계정, 메일 발송 구성을 확인 | 대상과 접근 권한 확인. 누락 구조와 기존 구조의 차이 기록 |
| 2. UX·기능·계측 구현 | 위 우선순위대로 화면 상태·저장·서버 권한·이벤트를 함께 연결 | 각 버튼의 기능·이벤트·실패 계약 구현 |
| 3. 시험 환경 검증 | 별도 시험 데이터로 정상·오류·권한·중복·복원 검증 | 핵심 시나리오 통과, 공개를 막는 결함 0 |
| 4. 운영 반영 | 호환 가능한 DB 변경 → 앱 배포 → 필요한 권한 제한 적용 | 운영 구성과 배포 버전 일치 |
| 5. 운영 확인 | 실제 외부 인증 메일·포텐스 응답·DB 저장·GA4 수신 확인 | 공개 URL에서 핵심 과업 완주와 계측 확인 |
| 6. 커뮤니티·SNS 공개 | 공개 글·링크 게시 후 자발적 이용·피드백 확인 | 운영 버전·게시 경로·게시 시각 기록 |
| 7. 보고서 대조 | 처리된 GA4 보고서와 통제된 시험·앱 기록 비교 | 누락·중복·환경 혼입을 설명할 수 있음 |

기존 공개 주소를 기준으로 배포 대상을 확인한다. 운영 DB를 시험 환경으로 잘못 연결하지 않는다. 운영 구조를 읽었더라도 기존 데이터의 이관과 역할별 권한 검증 없이 마이그레이션을 적용하지 않는다.

필수 검증은 다음을 포함한다.

- **가입·계정:** 외부 이메일 인증, 재발송·만료·복귀, 로그인 실패·세션 복원, 같은 기기의 계정 교체, 닉네임 저장·탈퇴.
- **사연·참여:** 등록·수정·삭제·취소, 연타와 통신 실패, 투표 변경 제한, 댓글·공감 중복, 새로고침 후 일치.
- **권한:** 작성자·타인·제3자·비로그인으로 개인 숨김, 비공개·재공개, 기존 AI 이용, 신규 AI 차단을 직접 API 요청까지 확인.
- **AI:** 정상 응답, 첫 실패 후 재시도, 부분 응답 후 오류, 완료 신호 없는 종료, 저장 실패, 동시 요청, 횟수 예약·반환.
- **평가·계측:** 평가 제출·건너뛰기·삭제, 동의·거부·철회, 중복 이벤트, 금지 정보 전송, 분석 장애 중 정상 기능 이용.
- **운영·기기:** 신고·문의 접수와 운영자 처리, 모바일 Safari·Chrome, 키보드·스크롤·뒤로가기.

실제 연동 검증과 오류를 주입한 시험은 구분해 기록한다. 결과는 `PASS / FAIL / NOT_RUN / BLOCKED`로 남긴다.

데이터 손실·타인 정보 노출·핵심 저장 장애가 발생하면 해당 기능을 중단하거나 검증된 버전으로 복구한다. DB를 파괴적으로 되돌리거나 기존 데이터를 삭제하는 방식으로 복구하지 않는다.

## 5. 공개 후 개선과 완료 판정

**커뮤니티·SNS 공개 후 실제 이용과 자발적 피드백부터 확인한다.** 2026-09-30 사용자 결정에 따라 직접 모집·진행자 동석 관찰은 당장 요구하지 않는다. 게시 경로·시각과 배포 버전을 기록하고 기술 시험 구간을 분리한다. 공개 게시를 통한 자발적 이용, 별도 직접 모집, 진행자의 도움을 받은 이용을 구분한다. 직접 관찰이나 인터뷰를 수행하지 않았다면 행동 데이터와 자발적 피드백만으로 확인한 범위를 명시한다.

아래 과업 관찰·인터뷰는 필요할 때 실행할 후속 방법이며 이번 공개의 선행 조건이 아니다.

관찰 과업은 ‘사연 찾기 또는 작성하기 → 원하는 AI 모드 선택 → 실제 대화 → 다시 찾기’로 구성한다. 버튼 위치를 미리 알려주거나 3턴을 억지로 채우게 하지 않는다. 실제 고민은 공개 가능한 범위에서 사용자가 선택하게 한다.

짧은 인터뷰에서는 세 가지를 확인한다.

- 무엇을 기대했고 어디에서 막혔는가?
- AI의 어떤 답변이 도움이 됐거나 도움이 되지 않았는가?
- 다시 이용한다면 어떤 상황에서 이용하겠는가?

개선은 다음 순서로 반복한다.

1. **수집 오류부터 구분한다.** 이벤트 누락이나 AI 장애를 UX 문제로 오인하지 않는다.
2. **문제의 근거를 묶는다.** GA4의 이탈·실패 지점, 실제 과업 관찰, 이용자의 설명을 함께 본다.
3. **한 번에 검증할 문제 하나를 선정한다.** 과업 중단·데이터 손실을 우선하고, 다음으로 반복되는 실패·발견성 문제를 본다.
4. **변경 전에 판정 기준을 적는다.** 대상 행동, 바꿀 요소, 기대하는 변화, 함께 확인할 부작용을 정한다.
5. **수정하고 새 버전으로 배포한다.** 관련 기능·권한·이벤트만 필요한 범위로 재검증한다.
6. **새 이용자에게 같은 과업을 확인한다.** 같은 사람이 사용법을 익힌 효과와 제품 개선을 구분한다.
7. **개선·악화·판단 보류로 기록한다.** 나아지지 않았다면 원복하거나 가설을 수정해 다시 검증한다.

GA4 비교에는 버전별 실제 분자·분모, 유입 경로, 기기, 신규·이어하기, 관찰 기간을 함께 남긴다. 공개 초기에는 작은 숫자를 퍼센트만으로 강조하지 않는다. 처리 중인 보고서는 잠정값으로 다루며, 일반 데이터 처리에 24~48시간이 걸릴 수 있음을 반영한다. [GA4 처리 시간](https://support.google.com/analytics/answer/11198161?hl=en)

**첫 개선 사이클의 완료물**은 정상 작동하는 운영 버전, 버튼·이벤트 목록과 검증 기록, 공개 이후 기준선, 실제 문제의 근거, 개선 배포, 동일 기준의 재검증 결과다. 결과에는 ‘기능 수정 확인’, ‘사용성 개선 관찰’, ‘정량 변화 관찰’, ‘표본 부족으로 판단 보류’를 구분한다. 배포 완료나 클릭 증가만으로 목표 달성을 선언하지 않는다.

이 계획이 최신 설계 기준이다. 기존 초안의 **3턴 대표 지표·고정 관찰 기간·성인 인증 포함 출시** 제안은 이번 결정으로 대체하며, 구현 착수 시 관련 문서도 함께 맞춘다.
