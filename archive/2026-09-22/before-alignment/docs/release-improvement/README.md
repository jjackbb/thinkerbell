# 니편내편 — 기능 검증부터 실제 개선 확인까지

작성: 2026-09-22 · 상태: **현재 상태 분석 완료 / 실행 계획 초안**

목표는 **기능 정상 작동 → 정확한 행동·성공 이벤트 → 검증한 버전 배포 → 실제 사용자 데이터와 관찰 → 개선 → 같은 기준으로 재측정**이다. 첫 검증 가치는 사용자가 **첫 사용 흐름과 AI 도움 여부**로 선택했다. 현재는 핵심 구현과 기존 배포가 있지만, 저장 실패 처리와 이벤트 정의에 문제가 있어 신뢰할 수 있는 개선 기준선을 만들기 전 단계다.

이번 요청에 따라 저장소 분석, 로컬 검사, 공개 배포 읽기 확인과 아래 설계를 수행했다. 구현·DB 변경·새 배포·GA4 설정 변경·실제 사용자 테스트는 이번 작업에서 실행하지 않았다.

## 현재 판단

- 현재 공개 URL과 `/api/health`는 200으로 응답한다. 로컬 타입 검사와 빌드는 통과했다.
- 배포 JS는 이번 로컬 빌드 JS와 바이트 단위로 같다. 그 HTML/JS에는 GA4 로더·측정 ID가 없었다.
- 사연·댓글 등에서 DB 실패를 확인하지 않고 성공 UI를 보여준다. 닉네임은 계정 저장 없이 변경되고, AI 오류 신고는 콘솔 출력만 한다.
- 기존 이벤트 9개는 재사용할 수 있지만, AI 턴 수·모드별 진입 시점·탭 단위 중복 방지 때문에 그대로 개선 지표로 쓰기 어렵다.
- 사용자가 GA4 미연결을 확인했다. 운영 DB 최신 상태는 미확인이고, DB 도구의 해당 프로젝트 조회는 권한 오류로 완료하지 못했다.
- 사용자가 제공한 Notion에서 2명의 인터뷰·시연 기록을 읽었다. 하단 탭·AI 버튼·등록 후 위치·삭제 동작 문제를 우선순위에 반영했다. 페이지 메타데이터는 7월이어서 9/4 30명 결과로 단정하지 않는다.

## 이번 대화에서 확정한 방향

- UX/UI 개선은 **사용자가 직접 담당**한다. 팀원은 필요성을 제기했으며 별도 수정안은 아직 없다.
- 기존 **사연→AI 경로의 가시성·모드 설명**부터 개선한다. AI 단독 신규 진입은 이번 첫 범위에 추가하지 않는다.
- 알림·구독 등 미연결 메뉴는 **준비 중임을 명확하게 표시**하고 핵심 흐름부터 완성한다.
- **나에게만 숨기기**와 **작성자의 전체 비공개**를 서로 다른 기능으로 제공한다. 비공개 동안 댓글·투표는 보관하고 타인의 접근·참여를 막으며, 재공개하면 복원한다.
- 비공개 전에 생성된 **기존 AI 대화는 보존·이용을 허용**한다. 해당 사연의 **새 AI 대화 생성만 차단**한다.
- AI 도움 여부는 **종료 시 선택 평가 1문항 저장 + 짧은 인터뷰**로 확인한다. 평가 내용은 GA4로 보내지 않는다.
- 확인이 필요한 선택은 임의 확정하지 않는다. 계획의 후보·추천과 사용자 결정을 구분한다.

## 실행 순서와 완료 기준

P0는 공개 전 막아야 할 기능·데이터·비용 문제, P1은 측정과 첫 사용 흐름, P2는 그 뒤 개선이다. 아래 시간은 마감 약속이 아닌 **개발 집중 작업량의 초기 추정**이다. 1일은 6시간으로 가정했고, 접근 권한·DB 차이·결함 수에 따라 달라진다. W1 이후 다시 산정한다.

| 순서 | 작업 묶음 | 구체적 결과 | 다음으로 넘어갈 기준 | 의존 / 담당 제안 / 초기 추정 |
|---|---|---|---|---|
| W0 | 목표·환경·과거 결과 정리 | 목표·GA4 미연결·Notion 인터뷰 확인; 운영 소유 프로젝트/접근 추가 확인 | 다른 프로젝트와 혼동 없음; 미확인 항목과 담당 명시 | 분석 일부 완료 / 사용자 + 작업자 / 잔여 0.5일 |
| W1 | 첫 사용 UX/UI 설계 + 기능·DB 계약 점검 | 홈/탭/사연 결과/AI 모드 시안, 운영 스키마와 로컬 migration 차이 | 사용자가 핵심 화면안·미결정 정책 검토; 기능별 저장·실패 행동 명확 | UX/UI 사용자, 기술 분석 작업자 / 기술 1~2일, 디자인 일정 별도 |
| W2 | P0 기능 정상화 | 저장 성공 확인, 실패 복구·초안 보존, AI 오류 처리·턴 집계, 서버 인증·사용량 제한 | 관련 정상·실패·권한 검증 통과, 거짓 성공 없음 | W1 / 구현 담당 / 2~4일 |
| W3 | 승인된 UX/UI와 버튼별 동작 적용 | 사연→AI 발견성·모드 설명, 준비 중 표시, 개인 숨김/작성자 비공개 분리 | 실제 기능·문구·실패 피드백 일치; 미정 정책은 승인 후 적용 | W1~W2 / 사용자 설계 + 구현 담당 / 1~3일, 비공개 정책에 따라 재산정 |
| W4 | 이벤트 구현·GA4 설정 | 안정적인 `button_id`, 일반 이벤트·성공 이벤트, 화면 이동, 버전·유입 구분 | 이벤트 명세와 코드·DB 허용 목록 일치; 개인정보 없는 payload | 정의 작업은 W1과 병행 가능, 성공 계측은 W2 뒤 / 1~2일 |
| W5 | 테스트 배포 검증 | 모바일/PC 핵심 흐름, 실제 저장·권한, GA4 DebugView/일반 보고서 증거 | P0 미해결 0, 핵심 시나리오·계측 확인 통과 | W2~W4 / 검증 담당 / 1~2일 |
| W6 | 운영 배포·기준선 시작 | 배포 SHA·URL·DB 변경·설정 기록, 운영 smoke 결과 | 운영 환경에서도 기능과 수집 확인; 수집 시작 시점 확정 | W5 / 배포 담당 / 0.5일 |
| W7 | 실제 사용·문제 선정 | GA4 분모/분자, 관찰·발언, 실패율·응답 시간, 개선 가설 1개 | 수집 오류와 사용자 문제 구분; 원인 가설에 근거 있음 | W6 / 사용자 모집·인터뷰 + 분석 담당 / 초기 관찰 7~14일 제안 |
| W8 | 선택한 개선 구현·재배포 | 가설 1개에 대응하는 변경, 관련 회귀 검증, 버전 구분 | 동작·수집 회귀 없음; 변경일·대상 기록 | W7 / 사용자 선택 + 구현·검증 / 1~3일 |
| W9 | 개선 효과 재확인 | 같은 조건의 전후 비교, 부작용, 유지/수정/보류 결정 | 실제 결과와 한계 기록; 개선 없음을 포함한 판단 | W8 / 분석 담당 + 사용자 / 비교 관찰 7~14일 제안 |

7~14일은 요일 차이를 줄이기 위한 운영 제안이며 통계적 충분성을 보장하지 않는다. 유입이 적으면 모집 방식이나 과업 테스트를 바꾸고, 정량 효과는 판단 보류한다. 실제 사용자 모집·관찰 기간은 구현 시간과 별개다.

## 첫 실행 묶음

1. [UX/UI 우선순위](04-ux-priorities-and-decisions.md)의 U01~U04에 대해 현재 화면→수정 후보→성공·실패 상태를 정리하고 사용자와 시안을 확정한다.
2. 디자인 검토 중 현재 Supabase 프로젝트 `vzhyhadjtaqbapicjrco`의 읽기 접근을 확보하고, 앱이 호출하지만 로컬 정의가 빠진 3개 테이블·4개 RPC를 대조한다.
3. 사연·댓글 저장 실패와 AI 스트림·성공 턴 집계를 우선 정상화한다. 화면이 아직 확정되지 않아도 정해진 기능 계약과 오류 재현 작업은 준비할 수 있다.
4. 합의한 화면에 버튼 ID·클릭/실패/성공 이벤트를 함께 구현하고 테스트 GA4에서 확인한다.

이 묶음의 완료는 배포·개선 효과 확인 전체의 완료와 다르다. W6 이후부터 실제 사용자 관찰을 시작한다.

개인 숨김/작성자 비공개, 기존 자료·AI 대화 처리, 평가 1문항 도입, 알림·구독의 준비 중 처리는 다시 묻지 않는다. 성인 확인 방식, 평가 문구·선택지·저장 기간처럼 남은 세부 선택은 검토 가능한 안을 만든 뒤 질문한다. 현재 요청은 분석·설계이므로 앱 변경은 별도 구현 요청에 따라 진행한다.

## 전체 완료의 의미

- 노출된 기능을 정상·실패·권한·새로고침 조건에서 검증했다.
- 주요 버튼의 이벤트, 실제 성공 이벤트, GA4 수집과 분모를 확인했다.
- 검증한 버전을 실제 운영에 배포하고 해당 환경에서 확인했다.
- 실제 이용 결과로 문제를 고르고 개선을 구현했다.
- 비교 조건을 명시한 실제 전후 결과로 유지/수정/보류를 결정했다.

**기능 완성, GA4 연결, 배포 성공 중 하나만으로 마지막 목표까지 완료했다고 기록하지 않는다.**
