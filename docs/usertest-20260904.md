### STEP 4 결과 — AI 상태 (2026-09-02)

**주력은 Potens AI**(`ai.potens.ai`), 예비는 Gemini다. 프로덕션에 직접 물어봐서 확인했다.

| | 상태 | 근거 |
|---|---|---|
| Potens (주력) | **정상** | 프로덕션 `/api/chat` 200 응답, 4.5초. 완주 테스트의 AI 3턴도 전부 이쪽이 답했다 |
| Gemini (예비) | **죽어 있다** | 일부러 주력을 실패시키면 예비로 넘어가는데, 구글이 `API key not valid`를 돌려준다. 프로덕션에 꽂힌 키가 무효다 (로컬 `.env`의 `GEMINI_API_KEY`는 아예 빈 값) |
| Potens 잔여 한도 | **모름** | 응답에 한도 정보가 없다. **potens.ai 대시보드에서 사람이 직접 봐야 한다** |

필요량 추산: 요청 1건당 약 1,100토큰(시스템 프롬프트 1,000 + 답변). 최악의 경우
30명 × 3대화 × 5턴 = 450건 ≈ 50만 토큰, 현실적으로는 100~150건 ≈ 15만 토큰.

**⚠️ 더 위험한 것 하나 — 그 자리에서 고쳤다 (PATCH-036).**
AI 호출이 실패해도 화면이 실패했다고 말하지 않고 **미리 적어둔 대사**를 AI가 한 말처럼
띄우고 있었다. 그런 길이 세 군데였다(요청 실패 / 빈 응답 / 서버에 쓸 수 있는 AI가 없음 —
마지막 것은 가짜 대사를 한 글자씩 흘려보내기까지 했다). 그대로 뒀다면 9/4에 Potens가
멈춰도 테스터는 "AI가 이상하다"고만 느끼고 **로그에는 3턴 도달로 찍혀 H3가 통째로
오염**된다. 이제는 `답장을 받지 못했어요` + `다시 보내기`가 뜬다.

**당신이 해야 할 일 — Gemini 키 넣기 (5분).** 키는 있다고 했으니 넣을 곳만 두 군데다.

1. **프로덕션(진짜 중요한 쪽):** Vercel → `thinkerbell` 프로젝트 → **Settings →
   Environment Variables** → 이름 `GEMINI_API_KEY`, 값에 키, 환경은 **Production** 체크 →
   저장. 저장만으로는 안 바뀐다. **Deployments 탭에서 최신 배포를 Redeploy** 해야 적용된다.
   (지금 그 자리에 무효한 키가 이미 들어 있으므로 **새 값으로 덮어쓰기**)
2. **내 컴퓨터:** 프로젝트 폴더의 `.env` 파일에서 `GEMINI_API_KEY=""` 줄의 따옴표 사이에
   키를 넣는다. (`.env`는 git에 올라가지 않으니 키가 공개될 걱정은 없다)

넣은 뒤 이 명령 한 줄로 예비선이 살았는지 확인할 수 있다 — `API key not valid`가 사라지고
한국어 인사가 오면 성공이다:

```
curl -s -X POST https://thinkerbell-eight.vercel.app/api/chat \
  -H "Content-Type: application/json" \
  -d '{"prompt":"한 문장으로 인사해줘","apiKey":"force-fallback"}'
```

### STEP 6·7 — 계측

**Supabase `events` 테이블이 주력, GA4는 병행.** 9/4 당일 저녁에 바로 SQL로 퍼널을
볼 수 있어야 하기 때문이다(GA4 상세 리포트는 하루 이상 걸린다).

```
events (id, session_id, user_id, event_name, props jsonb, created_at)
```

붙일 이벤트는 **6개뿐**:

| 이벤트 | 시점 |
|---|---|
| `app_open` | 첫 진입 |
| `login_success` | 로그인 완료 |
| `story_view` | 사연 상세 열림 |
| `vote_submit` | 투표 제출 |
| `ai_chat_start` | AI 대화 시작 |
| `ai_chat_turn3` | AI 대화 3턴 도달 |

## 무너질 경우의 방어선

**STEP 5가 하루에 안 끝날 가능성이 실제로 있다.** 그때는 앞의 4건(`#7 #8 #9 #19`)만
하고 나머지는 버린다. `#5`와 `#1`은 아프지만 테스트를 못 하게 만들지는 않는다.

**계측이 안 붙어도 9/4는 간다.** 관찰 기록지만 있으면 테스트는 성립한다.
반대로 STEP 1~4가 안 되면 그날이 통째로 날아간다. 우선순위가 뒤집히지 않게 한다.

## Day 2 — 9/4 현장 (STEP 10)

**로그는 어디서 멈췄는지만 알려주고, 왜 멈췄는지는 못 알려준다.**
30명이 눈앞에 있는데 로그만 보는 건 정보를 버리는 것이다. **관찰이 메인, 계측이 보조.**

  1. 다시 쓸 것 같나요? (아니라면 왜)
  2. AI랑 얘기해보니 어땠나요?
  3. 제일 별로였던 게 뭔가요?

카카오뱅크 서비스기획 공고 3건이 전부 **"데이터 분석을 통해 문제를 정의하고 서비스를

제외"** 라고 못 박았다.

이번 사이클 — **가설 → 30명 대면 테스트 → SQL 퍼널 분석 → 개선** — 이 그 요구에
그대로 대응한다. 지금 니편내편에 없는 단 하나가 실사용 데이터이고, 9/4가 그걸 메우는
날이다. 테스트 당일의 관찰 기록과 SQL 결과를 반드시 남겨둘 것. 그게 포트폴리오 원재료다.
