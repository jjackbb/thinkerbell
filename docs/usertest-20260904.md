### STEP 2 결과 — 2026-09-02 완주 기록

### STEP 4 결과 — AI 상태 (2026-09-02)

**주력은 Potens AI**(`ai.potens.ai`), 예비는 Gemini다. 프로덕션에 직접 물어봐서 확인했다.

| | 상태 | 근거 |
|---|---|---|
| Potens (주력) | **정상** | 프로덕션 `/api/chat` 200 응답, 4.5초. 완주 테스트의 AI 3턴도 전부 이쪽이 답했다 |
| Gemini (예비) | **죽어 있다** | 일부러 주력을 실패시키면 예비로 넘어가는데, 구글이 `API key not valid`를 돌려준다. 프로덕션에 꽂힌 키가 무효다 (로컬 `.env`의 `GEMINI_API_KEY`는 아예 빈 값) |
| Potens 잔여 한도 | **모름** | 응답에 한도 정보가 없다. **potens.ai 대시보드에서 사람이 직접 봐야 한다** |

필요량 추산: 요청 1건당 약 1,100토큰(시스템 프롬프트 1,000 + 답변). 최악의 경우
30명 × 3대화 × 5턴 = 450건 ≈ 50만 토큰, 현실적으로는 100~150건 ≈ 15만 토큰.

**⚠️ 더 위험한 것 하나 — 그 자리에서 고쳤다 (PATCH-036).**
AI 호출이 실패해도 화면이 실패했다고 말하지 않고 **미리 적어둔 대사**를 AI가 한 말처럼
띄우고 있었다. 그런 길이 세 군데였다(요청 실패 / 빈 응답 / 서버에 쓸 수 있는 AI가 없음 —
마지막 것은 가짜 대사를 한 글자씩 흘려보내기까지 했다). 그대로 뒀다면 9/4에 Potens가
멈춰도 테스터는 "AI가 이상하다"고만 느끼고 **로그에는 3턴 도달로 찍혀 H3가 통째로
오염**된다. 이제는 `답장을 받지 못했어요` + `다시 보내기`가 뜬다.

**당신이 해야 할 일 — Gemini 키 넣기 (5분).** 키는 있다고 했으니 넣을 곳만 두 군데다.

1. **프로덕션(진짜 중요한 쪽):** Vercel → `thinkerbell` 프로젝트 → **Settings →
   Environment Variables** → 이름 `GEMINI_API_KEY`, 값에 키, 환경은 **Production** 체크 →
   저장. 저장만으로는 안 바뀐다. **Deployments 탭에서 최신 배포를 Redeploy** 해야 적용된다.
   (지금 그 자리에 무효한 키가 이미 들어 있으므로 **새 값으로 덮어쓰기**)
2. **내 컴퓨터:** 프로젝트 폴더의 `.env` 파일에서 `GEMINI_API_KEY=""` 줄의 따옴표 사이에
   키를 넣는다. (`.env`는 git에 올라가지 않으니 키가 공개될 걱정은 없다)

넣은 뒤 이 명령 한 줄로 예비선이 살았는지 확인할 수 있다 — `API key not valid`가 사라지고
한국어 인사가 오면 성공이다:

```
curl -s -X POST https://thinkerbell-eight.vercel.app/api/chat \
  -H "Content-Type: application/json" \
  -d '{"prompt":"한 문장으로 인사해줘","apiKey":"force-fallback"}'
```

### STEP 6·7 결과 — 계측이 붙었다 (9/3 새벽)

**테이블** (`supabase/migrations/20260903000000_events.sql`, 운영 DB 적용 완료)

```
events (id, session_id, user_id, event_name, props jsonb, created_at)
```

- `session_id`는 **브라우저 탭 하나의 방문**이다(`sessionStorage`). 로그인 전 진입과
  로그인 후 행동을 잇는 유일한 끈이라, 로그인 때문에 끊기면 안 된다.
- 쓰기만 열려 있다. 둘러보는 사람(로그인 안 함)도 진입을 남길 수 있어야 퍼널의 분모가
  생기기 때문이다. **읽기 정책은 만들지 않았다** — 남이 볼 로그가 아니다.
- **아는 이름 9개만 받는다.** 오타나 실수로 심은 이벤트가 퍼널을 흐리지 않도록 DB가
  막는다. 실제로 모르는 이름을 넣어보니 400으로 거절됐다.

**기록 함수** (`src/lib/events.ts`)

- `track(name, props)` — 화면은 이 요청을 기다리지 않고, 실패해도 조용히 넘어간다.
  **계측이 서비스를 막는 일은 없다.**
- `trackOnce(key, name, props)` — 방문당 한 번만. 뒤로 갔다 다시 와도 숫자가 안 부푼다.
- GA4 자리는 이미 만들어 뒀다 — `window.gtag`가 있으면 같은 이벤트를 그쪽으로도 보낸다.
  측정 ID만 생기면 **계측 코드를 다시 손대지 않아도 된다.**

### 9/4 밤에 쓸 퍼널 SQL (미리 돌려봤다)

```sql
with base as (
  select count(distinct session_id)::numeric as n
  from public.events
  where event_name = 'app_open' and created_at >= date '2026-09-04'
),
steps(step_no, event_name, label) as (
  values (1,'app_open','① 진입'),
         (2,'login_success','② 로그인'),
         (3,'story_view','③ 사연 열기'),
         (4,'vote_submit','④ 투표'),
         (5,'ai_entry_click','⑤ AI 시작하기 누름'),
         (6,'ai_mode_select','⑥ 모드 선택'),
         (7,'ai_start_select','⑦ 대화방 열림'),
         (8,'ai_chat_turn1','⑧ 1턴'),
         (9,'ai_chat_turn3','⑨ 3턴')
)
select s.step_no, s.label,
       count(distinct e.session_id) as sessions,
       round(100.0 * count(distinct e.session_id) / nullif((select n from base),0), 1) as pct_of_open
from steps s
left join public.events e
  on e.event_name = s.event_name and e.created_at >= date '2026-09-04'
group by s.step_no, s.label
order by s.step_no;
```

**날짜 조건을 꼭 넣는다.** 9/2~9/3에 준비하며 쌓인 테스트 기록이 섞이면 숫자가 틀어진다.

가설 대조는 이 표에서 바로 읽힌다 — **H1**은 ③/①, **H2**는 ⑤/④ 와 ⑤→⑥→⑦ 낙폭,
**H3**는 ⑨/⑦.

**계측이 안 붙어도 9/4는 간다.** 관찰 기록지만 있으면 테스트는 성립한다.
반대로 STEP 1~4가 안 되면 그날이 통째로 날아간다. 우선순위가 뒤집히지 않게 한다.

## Day 2 — 9/4 현장 (STEP 10)

**로그는 어디서 멈췄는지만 알려주고, 왜 멈췄는지는 못 알려준다.**
30명이 눈앞에 있는데 로그만 보는 건 정보를 버리는 것이다. **관찰이 메인, 계측이 보조.**

- 1인당 5분. 옆에서 보면서 **"지금 뭘 하려고 하셨어요?"** 만 묻는다. 설명하지 않는다.
- 끝나고 구두 3문항:
  1. 다시 쓸 것 같나요? (아니라면 왜)
  2. AI랑 얘기해보니 어땠나요?
  3. 제일 별로였던 게 뭔가요?

## STEP 11 — 9/4 밤 분석

`events` 테이블에 SQL 한 방으로 퍼널을 뽑는다. 진입 대비 각 단계 도달률을 내고,
**H1·H2·H3가 맞았는지 대조**한다. 관찰 기록지에서 "왜"를 채운다.
