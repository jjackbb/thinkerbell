## 최우선 제보

사용자 제보: “아까 팀원이 로컬환경에서 비로그인 상태에서, 어떤 특정글은 삭제가 가능하던데..? 전체적인 오류 검증 해줘.”

확정된 DB 삭제 취약점으로 단정하지 말고 다음을 구분해:

- 삭제 버튼/확인창만 노출된 것인지, 화면 목록에서만 사라진 것인지.
- 성공 안내가 잘못 표시된 것인지, 실제 DB 행이 삭제된 것인지.
- 비로그인으로 보이지만 인증 세션이 남아 있었는지.
- 팀원과 현재 코드·빌드·브랜치·서버·포트·연결 DB가 같은지.

로컬 실행이라고 DB도 로컬이라고 가정하지 마. 제보의 상세 정보가 없더라도 현재 코드에서 독립적으로 조사 가능한 경로부터 확인해.

조사 단서(원인으로 확정된 것은 아님):

- `StoryCard.tsx`의 `isMyStory`는 `currentUser?.id === story.authorId`를 사용한다. 두 값이 없는 데이터에서 작성자로 잘못 판정되는지 확인해.
- `App.tsx`의 `confirmDeleteStory`는 authUserId를 확인하고 stories 직접 삭제에 authorId 조건을 붙인다.
- 화면의 소유자 판정·실제 인증 세션·서버/DB 권한은 각각 확인해. 프론트 조건만으로 안전하다고 결론 내리지 마.

비로그인·작성자·타인·운영자 역할을 분리하고 일반 사연·과거 데이터·작성자 정보 누락·숨김/비공개/블라인드 조건을 확인해. 토큰 없음/무효 토큰/일반 사용자 토큰의 실제 허용·거부를 대조해. 관리자 비밀키로 성공한 결과를 일반 사용자 권한의 증거로 쓰지 마.

기존 사연을 삭제해 시험하지 마. 별도로 만든 가상 데이터나 격리 환경을 사용해. 기존 계정이 테스트·팀원 계정이라는 결정은 재동의 전환 생략에 관한 것이며 기존 데이터 전체 삭제 승인이 아니다.

## 전체 오류 검증

화면·기능·권한별 목록을 먼저 만들고 위험도가 높은 순서로 실행해:

1. 인증/권한: 가입·중복 이메일·인증 복귀·로그인·로그아웃·재설정, 본인/타인 접근, 계정 전환 뒤 이전 데이터·권한 잔류.
2. 사연/참여: 목록·상세·작성·수정·삭제, 개인 숨김과 작성자 비공개, 투표·변경·댓글·공감, 연타·실패 후 재시도.
3. AI: 새 대화·이어하기·저장·복원·고정·삭제·평가·횟수, 동시 요청, 응답 실패와 저장 실패의 구분.
4. 계정/문의/공유: 마이페이지·설정·문의 역할별 접근, 공유·다운로드·모바일 화면·모달.
5. 분석: 일반 화면·클릭·결과 계측, 동의 전/거부/철회, 중복·누락, 민감 행동·원문·개인 ID 미전송.
6. 환경: 로컬·Preview·Production 코드/설정 차이, 콘솔·네트워크 오류, 잘못된 Supabase 연결.

각 항목은 PASS/FAIL/미검증/차단으로 구분하고 환경·역할·재현 순서·기대/실제 결과·근거를 기록해. 코드 검토·가상 응답·실제 API/DB·GA4 수신·사용자 관찰을 구분해. 제보를 재현하지 못한 것을 해결 완료로 표시하지 마.

명백한 코드 결함은 기존 정책에 맞춰 수정해. 권한 문제는 UI만 가리지 말고 서버/DB의 실제 거부도 확인해. 정책·운영 데이터 처리·권한 변경 방향이 애매하면 해당 부분만 보류하고 독립적인 작업은 계속해.

작고 되돌릴 수 있는 변경에 테스트를 새로 작성하지 마. 권한·데이터 손실·동시성 결함은 필요한 회귀 검증을 수행해. 통과한 검사는 새 변경·실패·미해결 문제 없이 반복하지 마.
