# 작성자 비공개 접근 경계 점검

2026-09-25, [PLAN](../../PLAN.md)의 비공개 계약을 현재 운영 DB 구조와 로컬 코드에 대조했다. **이 문서는 변경 설계·위험 점검이며, 비공개 기능을 운영 DB나 앱에 적용했다는 기록이 아니다.** 사연·댓글의 본문은 읽지 않았다.

## 확정된 이용자 동작

- 작성자 비공개는 작성자에게만 원문·기존 댓글이 보인다. 남의 사연을 나에게만 숨기는 `story_hides`와 별도 상태다.
- 비공개 사연은 마이페이지 ‘작성한 사연’ 안에서 공개·비공개로 구분한다. 재공개하면 보관한 댓글·투표를 다시 표시하되, 원래 `createdAt`을 유지한다.
- 다른 이용자는 목록·공유 링크·직접 API에서 원문과 댓글을 볼 수 없고 신규 댓글·투표·AI 대화방을 만들 수 없다. 기존에 소유한 AI 대화는 저장된 맥락으로 계속 이용할 수 있다. 작성자는 자기 비공개 사연으로 새 AI 대화방을 만들 수 있다.
- 변경 실패에는 화면 상태를 바꾸지 않는다. 비공개 안내에는 기존 타인 AI 대화에 사연 내용이 남을 수 있음을 표시한다.

## 현재 확인된 우회 경로

| 경로 | 관찰한 현재 상태 | 필요한 변경 |
|---|---|---|
| 사연·댓글 REST 조회 | `stories_select_public`, `comments_select_public`의 RLS 조건이 `true`라 익명·타인 조회가 가능하다. | 사연에 공개 상태를 추가하고 작성자 또는 공개 상태만 읽게 한다. 댓글은 부모 사연 접근 권한을 따라간다. 직접 URL과 REST ID 조회도 같은 결과여야 한다. |
| 댓글 직접 쓰기 | 로그인한 댓글 작성자만 검사하지만, 부모 사연의 공개 상태를 확인하지 않는다. | 새 댓글은 공개 사연에만 허용한다. 콘텐츠 검사 API 우회 경로도 별도로 닫는다. |
| 투표·공감·신고 함수 | `vote_story`는 사연 행을, `like_comment`는 댓글 행을 반환하는 `SECURITY DEFINER` 함수다. 후속 [댓글 공감 적용](2026-09-25-comment-likes-applied.md)에서 공감 함수는 현재 숨김·성인 사연을 거부하고 향후 `visibility='private'`도 거부하도록 준비했으며, 익명 실행 권한을 제거했다. 하지만 작성자 비공개 컬럼·정책은 아직 없다. `increment_story_view`와 `submit_report` 등 다른 함수의 비공개 경계도 별도 보완이 필요하다. | 각 함수가 부모 사연을 잠금·확인한 뒤 허용 대상에만 작동하도록 바꾸고, 행 반환 함수는 비공개 원문·댓글을 돌려주지 않게 한다. 실행 권한도 필요한 역할로 좁힌다. |
| 실시간 구독 | 앱은 사연·댓글의 새 행과 수정 행을 구독한다. 비공개 전 읽은 행은 이용자 브라우저 메모리에 남을 수 있다. | DB RLS가 새 변경의 전송을 거르더라도, 다른 이용자에게 비공개 전환을 알리는 **원문 없는 무효화 신호**와 재조회/제거가 필요하다. 실시간 권한을 실제 다른 계정에서 검증한다. |
| AI 대화 | 대화방 DB 정책은 현재 소유자만 검사한다. 로컬 `/api/chat-stream`은 대화방 소유자를 확인하고 DB에 저장된 지시문·이력을 읽도록 후속 수정했으나 운영 미배포·실제 계정 미검증이다. 새 대화방 생성은 아직 사연 공개 권한을 검사하지 않는다. | 새 대화방은 공개 사연 또는 자기 사연만 허용한다. 첫 답변 사용량을 서버에서 확인한다. 기존 타인 대화의 이어하기는 허용하되 비공개 원문을 재조회하지 않는다. |
| 화면 | 피드·주간/실시간 인기·공유 링크·마이페이지가 같은 사연 배열을 사용한다. | 공개 피드에서 비공개 행을 제외하고, 작성자만 마이페이지에서 공개·비공개를 구분한다. 공개 상태 변경은 DB 확인 뒤 반영한다. 정렬은 기존 작성일을 따른다. |

Supabase 공식 문서는 Postgres Changes의 새 행 전송에 테이블 RLS를 적용한다고 설명한다. 그러나 이미 읽어 둔 내용이 이용자 화면에서 즉시 사라진다는 보장은 아니다. `DELETE` 변경은 RLS로 개별 행 접근을 검증할 수 없으며, 일반적으로 이전 행에서 기본키만 전달된다. 그러므로 실시간 구독만 개인정보 보호의 근거로 삼지 않는다. [Realtime 권한](https://supabase.com/docs/guides/realtime/authorization), [Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes)

## 적용 순서와 검증 기준

1. 공개 상태·접근 함수와 무효화 신호를 로컬 마이그레이션으로 작성한다. 현재 사연 9건은 원문을 건드리지 않고 `public`으로 시작해야 하며, 단순 재공개가 `createdAt`을 바꾸지 못하게 한다.
2. 작성자 화면과 서버의 새 AI 대화방/기존 대화 권한을 연결한다. 비공개 전환 버튼은 직접 조회·RPC 차단 준비 전에는 노출하지 않는다.
3. 롤백 가능한 DB 역할 시험에서 익명·작성자·기존 대화 소유자·제3자 각각의 SELECT/INSERT/RPC 결과를 확인한다. 본문을 시험 출력으로 남기지 않는다.
4. 시험 계정의 실제 REST·Realtime·공유 URL에서 비공개 전·후·재공개를 검증한다. 이전에 열린 브라우저에서도 원문·댓글이 제거되는지 확인한다. 그 뒤에만 운영 기능을 켜고 배포 상태를 확인한다.

**현재 판정:** 설계 점검 완료, 구현·운영 적용·실제 계정 검증 `NOT_RUN`. 앞서 운영 DB에 적용한 것은 개인별 숨김 테이블이며 작성자 비공개가 아니다.

## 별도 결정이 필요한 과거 댓글 공감

같은 날 댓글 내용 없이 집계만 확인한 결과, 적용 전 운영 댓글 21건 중 3건의 `likeCount`가 0보다 컸고 합계는 31, 최대값은 16이었다. 기존 함수에는 계정별 공감 기록이 없어 이 숫자의 계정을 복원할 수 없었다. 사용자가 **0으로 재설정**하기로 결정했고 [계정별 공감 적용 기록](2026-09-25-comment-likes-applied.md)에 따라 운영 DB를 변경했다. 이는 작성자 비공개 기능의 완료 근거가 아니다.
