# GA4 이벤트 목적·화면 대조 기록

2026-09-25 기준 **결정·구현 대조 기록**이다. 최신 결정은 [PLAN.md](../../PLAN.md) §3, 이벤트·버튼의 상세 계약은 [버튼·이벤트 명세](../release-improvement/02-events-and-buttons.md)에 있다. 아래의 전체 이벤트 목록을 구현 완료로 읽지 않는다.

## 측정이 답해야 할 질문

첫 공개의 기능 검증은 버튼이 실제로 저장·응답·복원되는지 확인하는 것이다. 공개 후 GA4는 **분석에 동의한 이용자**가 `사연 상세 조회 → AI 진입 → 모드·설정 선택 → 첫 정상 AI 답변`의 어느 단계까지 갔는지 본다. 첫 답변 도달은 대표 지표이며, 도움을 받았다는 증거가 아니다. 도움 여부는 선택형 평가의 접근 제한 저장 결과와 짧은 관찰·인터뷰를 함께 본다. 개선 효과를 주장하려면 공개 기준선, 바뀐 화면/버전, 같은 과업의 후속 관찰과 다른 원인을 함께 대조한다.

| 이용 단계·현재 컴포넌트 | 후보 이벤트와 발생 시점 | 검증·개선에 쓰는 이유 |
|---|---|---|
| 첫 진입·가입: `WelcomeModal`, `LoginPromptModal`, `Header`, `Navbar` | 실제 화면 노출 `page_view`; 실제 버튼 활성화 `ui_click`; 인증 요청의 시작·결과; 이메일 확인 후 `sign_up` | 가입 시작과 완료, 게스트 둘러보기, 로그인 요구에서 멈춘 경우를 구분 |
| 사연 탐색·참여: `StoryCard`, `StoryDetailModal`, `CreateStoryModal`, 투표·댓글 UI | 상세 노출 `story_view`; 작성 시작 `story_create_start`; 서버 저장 확인 후 `story_publish_success`, `vote_submit`, `comment_create_success`; 차단·실패는 별도 | 관심 부족, UI 발견성, 권한/저장 오류를 클릭 수와 혼동하지 않음 |
| AI 진입·선택: 상세/피드 AI 버튼, `AIChatModeSelectionModal`, `AIExplainSettingsModal` | `ai_entry_click → ai_mode_select → ai_start_select` 또는 `ai_settings_confirm → ai_chat_open`; 횟수·로그인 차단은 `action_blocked` | AI를 찾지 못한 것과 찾았지만 선택·접근에서 막힌 것을 구분 |
| 첫 답변·이어하기: `AIChatView`, 대화 목록, `MyPageView` | 실제 요청과 완료/실패, 정상 완료 응답 첫 쌍에 `ai_chat_turn1`, 세 번째에 `ai_chat_turn3`; 저장된 방 다시 열기 `ai_chat_open(is_resume=true)` | 공급자/저장 장애와 첫 대화 도달, 다시 찾기 행동을 분리 |
| 마무리·도움 평가: `SessionSummaryCard`와 도입 예정 평가 UI | 실제 노출 `ai_feedback_view`, 저장 확정 후 `ai_feedback_submit`; 점수는 GA4 제외 | 평가 기회·응답 여부를 확인하되 점수를 행동 이벤트에 노출하지 않음 |

모든 노출 버튼은 기능 계약과 검증 사례를 가져야 하지만 **모든 클릭을 GA4로 보낼 필요는 없다**. 특히 위기 지원 버튼·원문·이메일·닉네임·계정/사연/대화 ID·평가값은 GA4 대상에서 제외한다. 단순 클릭은 사용 의도이며 저장·응답 성공이 아니다. 정확한 요청/대상별 성공 대조는 앱 내부 기록과 역할별 시험으로 확인한다.

## 이번에 수정한 코드와 아직 남은 차이

- `analyticsConsent.ts`와 `AnalyticsConsent.tsx`에서 첫 방문 비차단 배너, 동등한 거부/동의 버튼, 게스트·회원 마이 화면의 변경/철회를 구현했다. 미선택·거부 상태의 태그와 내부 선택적 이벤트 저장을 막는다. 이미 태그가 로드된 탭에서는 철회 직후 [Google 공식 `ga-disable-측정ID` 차단](https://developers.google.com/tag-platform/security/guides/privacy#turn_off_google_analytics)을 적용하고 이 사이트의 `_ga` 쿠키를 지운다. 새로 연 탭에도 거부 상태를 먼저 적용한다. 이미 GA4에 수집된 서버 데이터 삭제 기능은 아니다.
- `ga4.ts`는 명시적 동의 뒤에만 태그를 로드하고 `send_page_view: false`로 설정했다. 페이지뷰는 앱 탭 전환 때 수동 전송하며 쿼리·해시 없는 URL, 고정 제목, 출처 도메인만 사용한다. `events.ts`는 GA4와 내부 DB 삽입을 독립시켰고 GA4 속성을 허용 목록으로 제한해 탭 UUID, 사연·페르소나 ID, 원문을 제외했다. [수동 페이지뷰 안내](https://developers.google.com/analytics/devguides/collection/ga4/views)
- `AIChatView.tsx`는 스트림의 명시적 `done` 또는 `[DONE]`과 비어 있지 않은 답변을 받은 뒤 화면에 표시한 응답만 첫/세 번째 완료 턴으로 센다. `error`나 완료 신호 없는 부분 응답은 실패로 표시한다. 이후 `ai_personas` 저장 결과를 따로 확인해 실패 시 화면에 경고·재시도 버튼을 보이고, GA4 결과 이벤트 `operation_success/error(operation=ai_reply_save)`로 분리한다. 저장 전 화면을 벗어나거나 탭을 닫는 경우, 공급자 스트림 형식, 실제 DB 저장/복원은 원격 과업 검증이 남아 있다.
- 운영 `events` 테이블은 기존 9개 이름만 허용한다. 따라서 새 저장 결과 이벤트는 **GA4 전용**이며 내부 DB 결과 로그라고 주장하지 않는다. 운영 DB 마이그레이션은 구조·RLS·기존 데이터 대조 후 별도 적용한다.
- `App.tsx`의 사연 조회·투표 이벤트에는 여전히 정확한 서버 성공/노출 판정 확인이 필요하고, 사연 등록·댓글 작성 성공 등 상세 명세의 다수 이벤트는 아직 구현하지 않았다. 버튼 전체를 클릭 계측했다고 주장하지 않는다.
- 사용자가 모바일 첫 진입에서 **로그인 또는 게스트 둘러보기 선택 뒤에 동의 배너를 보여주는 순서**를 선택했다. `App.tsx`는 환영/로그인 모달이 열려 있는 동안 배너를 렌더링하지 않도록 변경했다. 가입·로그인 전에 거부/동의 선택을 요구하지 않으며, 선택 전 행동은 소급 전송하지 않는다. 390×844 임시 모바일 브라우저에서 첫 진입은 환영 화면 표시·배너 미표시, 게스트 선택 후에는 환영 화면 종료·거부/동의 배너 표시를 확인했다. 실제 모바일 Safari·운영 배포 확인은 남아 있다.

## 사용자가 확정한 판단

1. **대표 경로:** 사연 상세 조회 → 첫 정상 AI 답변. `ai_chat_turn1`은 답변이 정상 종료돼 화면에 표시된 때로 확정했고, 저장 결과는 별도 결과로 보낸다.
2. **동의 화면:** 첫 방문에 서비스 이용을 막지 않는 배너를 보이며 거부해도 계속 이용할 수 있다. 게스트·회원 마이 화면에서 변경/철회한다. 미동의 기간 행동은 소급 전송하지 않는다.
   모바일에서는 먼저 로그인하거나 게스트로 둘러보기를 선택한 뒤 배너가 나타난다.
3. **시험 데이터 분리:** 니편내편 GA4 계정에 `니편내편 QA` 속성(ID `555775628`)과 별도 웹 스트림(ID `15839872612`, 측정 ID `G-04B9P59SNE`)을 생성했다. 스트림 URL은 GA4가 `localhost:3000`을 거절해 기존 공개 URL을 등록했지만, 실제 QA 빌드에서만 QA ID를 사용한다. QA 스트림의 향상된 측정은 끔으로 확인했다. 운영 ID는 `G-WP7J6TVNFK`다. 두 속성 모두 `ai_chat_turn1`을 코드로 전송하는 **주요 이벤트**로 미리 등록했으며, 금전 기본값 없이 세션당 1회로 설정했다. 실제 AI 이벤트 수신은 없다. [Google의 사전 주요 이벤트 등록 안내](https://support.google.com/analytics/answer/12946393?hl=en-419)

로컬 QA 서버(`http://127.0.0.1:3000/`)의 브라우저에서 처음에는 Google 태그/요청 0, 거부 후 0, 설정에서 동의 후 QA ID 로더 1개와 `page_view(screen_name=mypage)` 수집 요청 1개를 확인했다. `gtag` 설정에는 `send_page_view:false`였고 URL 쿼리·사연/계정 ID는 없었다. QA 속성 실시간 개요에도 `page_view` 1건과 활성 사용자 1명이 표시됐다. GA4 자동 이벤트 `first_visit`, `session_start`, `user_engagement`도 각 1건 표시됐다. 이는 로컬 시험 데이터이며 실제 이용자 퍼널이 아니다.

처음 철회 시험은 화면 전환 직후 추가 요청이 없었으나, 기존 태그가 살아 있는 탭에서 시간이 지나 `_ga` 쿠키가 다시 보였다. 이에 Google의 `ga-disable` 플래그를 철회 즉시 적용하고 새로고침 시 거부 상태를 먼저 반영하도록 고쳤다. 재시험에서는 철회 직후 및 탭을 백그라운드로 둔 4초 뒤에도 차단 플래그 `true`, GA 쿠키 0개, 추가 수집 요청 0건이었다. 이 관찰은 해당 브라우저·짧은 시간에 한정되며 장시간·다른 기기와 실제 운영 배포의 검증은 남아 있다. 운영 `VITE_GA4_ID`는 아직 설정하지 않았다. 실제 공급자 스트림·DB 저장 성공/실패 과업도 아직 시험하지 않았다.
