# AI 첫 답변·이용 횟수 경계 — 2026-09-28

최신 계약은 [PLAN](../../PLAN.md)이다. 남의 사연으로 **새 AI 대화의 첫 정상 답변이 완료될 때** 한국 시간 기준 하루 3회 중 1회를 차감한다. 실패·완료 전 취소는 예약을 돌려주고, 내 사연·이미 정상 이용한 대화 이어하기는 추가 차감하지 않는다.

## 현재 확인한 차이

| 경로 | 확인한 동작 | PLAN과의 차이 |
| --- | --- | --- |
| [화면 횟수](../../frontend/src/lib/aiQuota.ts) | 브라우저가 `ai_chat_usage`를 직접 읽고 INSERT한다. 조회·저장 실패 때 `localStorage` 숫자로 대체한다. | 서로 다른 기기·동시 요청의 상한을 서버에서 강제하지 못한다. 실패한 DB 조회를 남은 횟수로 오인할 수 있다. |

| 운영 DB 정책 | 읽기 전용 MCP 메타데이터에서 `ai_chat_usage_insert_own`, `ai_personas_insert_own`이 인증 계정의 직접 INSERT를 허용함을 확인했다. | 서버가 나중에 횟수를 세더라도, 브라우저가 임의 대화방·지시문을 만들 수 있다. |

화면의 [한도 안내](../../frontend/src/components/PremiumModal.tsx)에 있던 ‘지금 한 번 둘러보기’는 제한을 건너뛰고 일반 대화방을 여는 경로였다. 로컬 코드에서 제거하고 구독은 ‘준비 중’으로 표시했다. 이는 **한 우회 버튼의 제거**이며 서버 횟수 제한 완료가 아니다.

사용자는 한도 도달 후 **내 사연과 기존 대화로 이동 안내**를 선택했다. 로컬 화면에는 ‘내 사연 보기’와, 저장된 대화방이 있을 때만 ‘기존 대화 이어가기’를 연결했다. ‘내 사연 보기’는 마이페이지의 작성한 사연 탭으로, 기존 대화는 AI 대화방 목록으로 이동한다. 새 대화를 더 만들 수 있는 미리보기 경로는 열지 않는다.

## 연동 전 구현 순서

1. 서버가 사연 접근 권한과 사용자 소유를 확인해 새 대화방을 만든다. 시스템 지시문·사연 ID·대화 모드를 브라우저가 임의로 저장해 권한을 바꿀 수 없게 한다. 기존 대화는 소유자가 계속 열 수 있도록 읽기·수정 경로를 별도로 검증한다.
2. DB에서 사용자·한국 날짜별 예약/완료를 원자적으로 기록한다. 같은 방의 첫 요청 재시도와 다른 방의 동시 요청을 분리한다. 실패·완료 전 취소, 서버 중단 후 미완료 예약 회수까지 시험한다.
3. `/api/chat-stream`이 예약 성공 뒤 공급자에게 요청하고, 완료 신호와 비어 있지 않은 답변을 확인한 뒤 한 번만 완료한다. 응답이 없거나 부분 응답으로 끝나면 예약을 반환한다. UI는 DB의 확정 잔여 횟수를 표시하고, 조회 실패를 `localStorage` 성공으로 바꾸지 않는다.
4. 별도 시험 데이터로 두 계정·두 탭·자정·실패·재시도·직접 API를 검증한 다음, 클라이언트의 직접 `ai_chat_usage` INSERT와 임의 새 `ai_personas` INSERT를 닫는다. 운영 적용 전에는 현행 브랜치를 공개 배포하지 않는다.

운영 `ai_chat_usage`는 `id`, `userId`, `storyId`, `usedAt`, `usedOn`만 가지며 예약 상태·대화방 ID·중복 방지 키가 없다. `ai_personas`는 `storyId`, `systemInstruction`, `chatHistory`를 가지나 브라우저 직접 INSERT/UPDATE가 가능하다. 구조·정책 조회는 성공했으나 기존 대화 본문이나 사용자 식별 데이터는 읽지 않았다. 서버 횟수 제한과 실제 계정 시험은 **NOT_RUN**이다.

## 사용자 확정 전환·시험 순서

- 새 서버 횟수 규칙을 적용하는 날의 기존 사용 기록은 방을 연 시점에 차감한 값이다. 완료된 답변인지 추측해 이관하지 않는다. **새 코드와 DB가 준비된 배포일 이후 맞는 다음 한국 시간 0시**부터 새 규칙을 시작한다. 이 시각 전까지 기존 기록을 소급해 새 규칙의 완료 기록으로 바꾸지 않는다. 실제 활성화 시각은 배포 기록에 남긴다.
- 격리된 로컬 Supabase 환경에서 예약·완료·반환과 두 계정·두 탭·자정·오류를 먼저 검증한다. 그 후 새로 만든 **전용 이메일 계정 두 개**로 일반 가입·이메일 확인을 거쳐 운영 REST·브라우저 최종 확인을 한다. 실사용 계정의 대화·사연을 시험 자료로 쓰지 않는다. 사용자는 신규 전용 계정 방식을 선택했으며 계정 생성·가입 시험은 아직 확인하지 않았다.
- 위 순서는 시험·전환 방침이다. 전환용 서버·DB 구현이나 자정 활성화가 완료됐다는 뜻이 아니다.

## 사용자 확정 날짜·보관 규칙

- 사용자는 **요청일 기준**을 선택했다. 23:59에 첫 실제 AI 요청을 서버가 받아 예약하고 00:01에 첫 정상 답변이 완료되면 전날의 3회 중 1회로 확정한다. 실패·완료 전 취소는 그 예약을 돌려준다. 대화방을 연 시각은 기준이 아니다. 전날 시작한 요청이 자정 뒤 완료되면 새날에 화면에서 확인되는 완료 답변이 3건을 넘을 수 있다는 한계를 함께 설명했다.
- 사용자는 **횟수 처리 기록 30일 보관**을 선택했다. 예약이 완료·반환·만료되어 종료된 뒤 30일 동안 중복·오차 문의를 확인할 수 있도록 한다. 계정·요청·대화방 식별자, 한국 날짜, 상태와 처리 시각 등 필요한 운영 정보만 대상이며 대화 본문·이메일·IP·GA4 이벤트·도움 평가의 보관 기간을 뜻하지 않는다. 운영에는 테이블·자동 삭제 작업을 아직 적용하지 않았다.

## 격리 DB 초안과 검증

[SQL 초안](sql/ai-quota-reservations-draft.sql)은 요청별 상세 처리 기록과, 기존 대화에 다시 차감하지 않기 위한 **서버 전용 대화방 상태**를 분리한다. 상세 기록은 종료 후 30일에 삭제하도록 함수를 준비했다. 대화방 상태에는 요청 날짜·결과·본문을 담지 않고 방이 삭제될 때 함께 제거한다. 브라우저 역할은 이 두 테이블과 처리 함수에 직접 접근할 수 없도록 초안에 권한을 명시했다.

격리된 Supabase PostgreSQL 이미지에서 [계약 시험](../../tests/ai-quota-reservations-contract.sql)과 [동시 요청 시험](../../tests/run-ai-quota-local.sh)을 통과했다. 요청일 고정, 자정 후 완료, 같은 요청 재시도, 실패 반환, 만료된 요청 거부, 두 프로세스가 마지막 한 자리를 동시에 요청할 때 1건만 허용, 30일 정리 후 기존 방 재차감 방지, 서버 역할 실행을 확인했다. 운영 DB는 읽기 조회만 했으며 실제 계정·REST·브라우저 검증은 **NOT_RUN**이다.

이 SQL은 **운영 미적용 초안**이다. 첫 답변을 서버에 정상 저장한 뒤에만 완료 함수를 호출하도록 서버·화면을 연결해야 한다. 기존 `ai_chat_usage` 직접 쓰기와 `ai_personas` 임의 생성·수정 권한을 닫기 전에는 공개 배포하지 않는다. 예약 유효 시간은 서버 요청 제한과 함께 맞춰야 하며, 30일 정리 함수의 실행 일정도 아직 연결하지 않았다. 기존 대화방과 전환 전 사용 기록은 소급 이관하지 않는다.

## 2026-09-28 로컬 후속 구현과 남은 경계

- `POST /api/ai/rooms`는 로그인 계정으로 저장된 사연을 확인하고 새 방의 지시문을 서버에서 만든다. 기존 요청 ID 또는 같은 사연·모드·설정의 방이 있으면 재사용한다. 작성자 자신의 비공개 사연은 허용하고, 다른 이용자의 비공개·성인·블라인드·개인 숨김 사연의 신규 방은 거부한다. 중복 선택을 원자적으로 막을 [고유 인덱스 초안](sql/ai-room-choice-unique-draft.sql)은 격리 PostgreSQL에서 시험했으며 운영에는 미적용이다. 운영 `stories`에는 아직 `visibility` 열이 없으므로 비공개 허용 시험은 미래 구조를 흉내 낸 로컬 HTTP 시험이다.
- `GET /api/ai/quota`는 `AI_QUOTA_ACTIVATES_AT`이 없거나 미래이면 기존 사용 기록을, 유효한 한국 시간 0시 이후이면 서버 예약·완료 기록을 읽는다. 잘못된 시각은 오류로 막고, 방 생성 전에 설정을 검사한다. 실제 전환 시각은 설정하지 않았다.
- 공급자 SSE는 합성 문장 1건의 실제 포텐스 호출에서 `text` 이벤트 6개와 `done` 이벤트 1개를 관찰했다. 답변 내용·토큰은 기록하지 않았다. 로컬 파서는 청크 분할·빈 답변·부분 종료·오류를 시험했으며, 정상 종료가 없으면 화면에 완료를 보내지 않는다. 이 호출은 실제 앱 로그인·DB 저장 시험이 아니다.
- 화면의 대화 상태는 스트리밍 중 메모리에서만 바뀐다. 답변이 정상 종료된 후에만 `ai_personas.chatHistory`를 저장하며, 실패 후 재시도는 이전 실패 말풍선을 교체한다. 다만 이 저장은 아직 브라우저의 직접 DB 업데이트여서 서버 차감과 원자적으로 묶이지 않는다.
- 새 제한을 활성화하면 `/api/chat`·`/api/chat-stream`은 현재 `AI_QUOTA_NOT_READY` 503을 반환한다. 예약·저장·완료/반환 연동, 직접 `ai_chat_usage` 쓰기와 임의 `ai_personas` INSERT/지시문 UPDATE 제한, 30일 자동 정리, 실제 계정·브라우저·운영 배포는 **NOT_RUN**이다. 이 브랜치는 공개 준비 완료가 아니다.

로컬 `npm run lint`, `npm run build`, AI 방/스트림·사연 재시도 모의 HTTP 시험 12건은 통과했다. 격리 PostgreSQL의 예약·동시성·방 선택 인덱스 계약 시험도 통과했다. 두 시험 모두 운영 DB 변경이나 공개 브라우저 경험을 입증하지 않는다.

운영 DB에서 대화 내용 없이 **구조 집계만** 다시 조회했다. 기존 방 7개 중 이력 0개가 2개, 사용자 발언과 AI 발언이 모두 들어 있는 방이 4개, 사연 ID가 없는 방이 2개다. 과거 자동 저장은 실패한 사용자 발언·부분 응답도 이력에 남길 수 있었으므로 이 집계만으로 어떤 방이 첫 정상 답변을 받은 것인지 판정할 수 없다. 전환 전 방의 무료 이어하기 범위를 사용자와 확정하기 전에는 기존 방을 새 완료 기록으로 추정 이관하지 않는다.
