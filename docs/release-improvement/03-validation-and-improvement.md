# 기능 검증·실제 개선 확인 명세

최신 실행 순서·판정 기준은 [PLAN.md](../../PLAN.md) §4~5를 따릅니다. 이 문서는 세부 시험·기록 양식입니다.

작성: 2026-09-22 · **실행 전 명세**. 아래 시나리오의 결과는 현재 모두 NOT_RUN이다. 폴더 정리 전 수행한 타입/빌드/HTTP 확인은 [현재 상태](01-current-state.md)에 별도 기록했다.

사용자 확정 목표: **첫 사용 흐름과 AI 도움 여부**. UX/UI는 사용자 본인이 담당하며 수정안은 아직 없다. 기존 사연→AI 가시성·모드 설명부터 개선하고, 알림·구독은 준비 중 표시, 개인 숨김과 작성자 비공개는 별도 제공하기로 결정했다.

추가 확정: 비공개 동안 댓글·투표는 보관하고 타인의 접근·참여를 막으며 재공개 시 복원한다. 기존 AI 대화는 보존·이용 허용, 타인의 새 대화 생성은 차단하되 작성자는 자기 비공개 사연으로 새 대화를 만들 수 있다. 기존 공감 대화의 관점 변경은 저장된 맥락을 사용한다. 종료 시 선택 도움 평가 1문항을 저장하고 짧은 인터뷰로 보완하며, 평가 내용은 GA4에 보내지 않는다.

## 1. UX/UI 개선을 시작하는 기준

참고 원본: [Notion 유저 인터뷰·시연 기록](https://app.notion.com/p/3a9626093f2e80439a91f9946d6c5ba3). 두 인터뷰이의 실제 시연 메모와 답변이 있으나, 30명 시험 결과나 개선 효과를 보여주는 자료는 아니다.

| 먼저 다룰 문제 | 원본 근거 | 팀 UX/UI 결과물 | 기술·측정 작업 |
|---|---|---|---|
| 현재 위치와 이동 버튼을 못 찾음 | 하단 탭 발견 못 함, 가입 후 마이페이지 혼란 | 홈 진입·현재 탭·주요 CTA의 위치/문구/상태 | 신규 가입/기존 로그인/게스트 전환 검증, 화면·nav 클릭 |
| 사연 등록 후 결과를 못 찾음 | 내 사연이 어디 올라갔는지 어려움 | 등록 진행·성공 상세·실패 초안 상태 | 현재 상세 전환 구현은 있음. DB 성공을 확인한 뒤 열리고 새로고침해 남는지 재검증 |
| AI 진입이 안 보이거나 의미가 불명확 | AI 버튼 가시성, 상대 역할 대화에 대한 기대 차이 | 눈에 띄는 AI 진입과 상황/공감 차이를 설명하는 짧은 문구 | mode/entry별 진입→실제 첫 답변, 도움 평가 |
| 의도치 않은 삭제·중복 | 삭제 확인 없이 지워짐, 댓글 중복 관찰 | 확인/취소·저장중·완료·실패 상태 | 사연 삭제 확인은 현재 존재하므로 재검증부터. 댓글 DB 중복/연타/Realtime 검증 |
| 정보의 뜻을 혼동함 | 주간/실시간 랭킹 혼동, 본인 글 투표 안내 가시성 | 명확한 라벨과 참여 가능 조건 | 실제 정책과 화면 문구 일치, 버튼 blocked 사유 |

사용자가 화면별 **목적 → 버튼 → 성공 결과 → 로딩 → 빈 상태 → 오류 → 로그인/한도 → 뒤로가기**를 판단할 수 있도록 작업자가 시안·대안·근거를 준비하고, 확정 뒤 API·저장·이벤트와 연결한다. 별도 팀원의 디자인 작업을 기다리는 단계는 두지 않는다. 실제 일정은 아직 확정하지 않았다.

기능 고장 수정과 이벤트 정의는 디자인 검토와 병행할 수 있다. 버튼의 실제 위치/문구 변경과 계측 삽입은 같은 변경 묶음에서 처리한다. 이미 수정된 과거 문제는 다시 구현하지 않고 현재 화면에서 재검증한다.

**전체 화면을 예쁘게 바꾸는 것을 선행 조건으로 삼지 않는다.** 근거가 있는 첫 사용 흐름부터 팀과 범위를 정한다. 취소 투표, 개인 비공개 AI 우선 진입 같은 요청은 기존 투표 변경 제한/사연 기반 AI 구조를 바꾸므로 별도 정책·범위 선택이다.

## 2. 검증 환경과 기록 방식

- 테스트 대상: 수정 완료 commit SHA, 디자인 버전, DB migration 목록, 이벤트 schema version, 배포 URL을 고정한다.
- 데이터: 테스트 환경의 A(작성자), B(타인), C(제3자), 비로그인, 운영자 계정. 실제 개인 고민 대신 테스트용 합성 사연을 쓴다.
- 기기: 모바일 Safari·모바일 Chrome 핵심 흐름, 데스크톱 Chrome·키보드. 뷰포트 시뮬레이션과 실제 폰 검증은 구분한다.
- 정상/오류: 실제 테스트 DB·AI 연동과 모의 네트워크 실패를 구분해 기록한다. 실제 공급자 응답은 소수의 합성 입력으로 확인하고, 다수 오류·한도 시나리오는 모의 공급자를 사용한다.
- 증거: `case_id, revision, environment, actor, preconditions, steps, expected, actual, status, evidence, defect_id`.
- 상태: `PASS / FAIL / NOT_RUN / BLOCKED`. 테스트를 설계했다는 이유로 PASS로 바꾸지 않는다.

운영 DB의 기존 자료는 삭제하거나 시험용으로 재사용하지 않는다. 공개 배포에서 필요한 smoke는 테스트 계정·표시된 시험 데이터로 범위를 좁히고 원복 대상을 기록한다. 접근 권한이 없으면 해당 검증은 BLOCKED이며 다른 환경 결과로 대신 통과시키지 않는다.

권한 검사는 UI에서 버튼이 안 보이는 것만으로 끝내지 않는다. 시험 환경에서 서버가 비로그인·타인 요청을 거절하는지 별도 확인한다.

## 5. 배포 순서와 복구

1. **준비:** 팀 UX/UI안, 테스트 결과, 대상 Git/Vercel/Supabase, 새 환경변수 이름·범위, DB 변경 목록, 비용 제한, 알려진 제한을 한 묶음으로 만든다.
2. **테스트 환경 DB:** 누락 migration을 복원하고 RLS/함수·새 이벤트 허용 목록을 먼저 검증한다. 원격 DB 구조가 확인되지 않으면 임의 DDL을 적용하지 않는다.
3. **Preview:** 동일 수정 SHA를 배포해 T/Q 필수 케이스를 실행한다. 운영 DB를 자동 공유해 사용자 데이터를 변경하지 않게 환경 연결을 확인한다.
4. **출시 판단:** P0 미해결 0, 핵심 기능 및 Q01~Q11 통과, 미실행/낮은 우선순위의 제한과 담당 명시. 실제 배포 실행 전 이 결과를 검토할 수 있게 준비한다. 폴더 정리 작업만으로 배포 검증을 통과시키지 않는다.
5. **운영 DB 확장→앱 배포:** 구버전도 읽고 쓸 수 있는 변경부터 적용하고 앱을 배포한다. Vite GA4 ID 등 빌드 값과 서버 AI 키를 구분한다.
6. **운영 smoke:** 공개 접속만이 아니라 로그인→사연/투표→두 모드 AI 응답→저장 복원→계측을 좁은 시험 범위로 확인한다. Preview 합격을 운영 합격으로 대신하지 않는다.
7. **기준선 개시:** 운영 핵심 과업·실시간 수신을 확인한 첫 공개 버전을 기준선으로 삼고 측정 시작 시각을 기록한다. 링크 공개와 직접 모집을 병행한다. 일반 보고서는 처리 후 통제 시험·앱 기록과 대조하며 보고서 대기를 고정된 공개 유예 기간으로 만들지 않는다. QA 데이터는 분리한다.
8. **복구:** 데이터 손실·타인 정보 노출·로그인/핵심 저장 장애·AI 무제한 비용·계측 정의 붕괴 시 해당 릴리스를 중단/직전 검증 버전으로 복귀한다. 추가 테이블은 즉시 삭제하지 않고 호환 상태로 남겨 조사한다. 이후 장애 시간·영향 사용자를 비교 분석에서 분리한다.

실제 Vercel 프로젝트 연결 정보(`.vercel/project.json`)는 로컬에 없었다. 배포 전 앱 소유 프로젝트를 확인하고 공개 URL만 보고 CLI를 임의 연결하지 않는다. 현재 Supabase MCP 접근 오류의 해결 방법은 해당 프로젝트 권한이 있는 계정/연결로 확인하는 것이다.

## 6. GA4에서 만들 보고서와 지표

모든 보고서에 `event_schema_version=2`, production, 비교 release/UI 버전, 날짜 범위, 내부 QA 제외를 적용한다. 모바일/PC, 유입 경로, 신규/재방문, 로그인/게스트, AI mode/is_resume을 필요에 맞게 나눈다. 모집 UT와 자연 유입을 한 표본으로 합치지 않는다.

| 보고서/질문 | 정의 | 해석 한계 |
|---|---|---|
| 첫 진입 | 유효 방문→피드/상세→참여/AI 진입의 사용자 도달 수 | 페이지 조회 수를 사람 수로 세지 않음 |
| 버튼 발견·작동 | 해당 화면을 본 사용자 중 특정 button_id를 사용한 사용자 | 버튼 미클릭이 '못 찾음'인지 '필요 없음'인지는 관찰 필요 |
| AI 진입 | ai_entry_click→mode→opening 또는 settings→chat_open→turn1→turn3 | 모드별 가지를 분리, 투표는 필수 단계에서 제외 |
| 작성 흐름 | story_create_start→서버 publish_success | 폼을 연 사람·입력한 사람·등록 시도자를 구분 |
| 기술 실패 | request별 실패 수 / 실제 request 수, operation별 | 클릭 수를 분모로 쓰면 로그인 차단·단순 재클릭이 섞임 |
| AI 응답 시간 | 첫 텍스트/전체 완료의 중앙값·상위 지연 값, 표본 수 | GA4 맞춤 metric 외 정밀 분포는 앱 로그; 실패·중단을 0초로 기록하지 않음 |
| 도움 여부 | 평가 긍정/중립/부정 수, 응답률, 인터뷰 이유 | 평가 내용은 접근 제한 자료에서 분석; 미응답을 긍정으로 취급하지 않음 |

**대표 행동 지표:** 관측된 첫 방문 세션 중 사연 조회 → 첫 정상 AI 답변(`ai_chat_turn1`) 도달 비율. 같은 기간·버전·관측 세션에서 중복 제거한다. `ai_chat_turn3`는 추가 이용 지표다. 한도·인증 오류로 막힌 시도는 별도 실패 분기로 보여주고 임의로 빼서 전환율을 높이지 않는다. 게스트 미리보기는 분리한다.

GA4 사용자 기반 퍼널 결과를 세션 도달률이라고 바꾸어 부르지 않는다. 대표 지표는 관측된 첫 방문 세션 단위로 집계하고 성공 턴 발행·순서는 앱 기록으로 대조한다. 동의·차단 때문에 관측되지 않은 이용자를 포함한 전체 전환율로 일반화하지 않는다.

**도움 지표:** “이 AI 대화가 도움이 되었나요?”의 4~5점 응답 수 / 전체 유효 응답 수. 전체 점수 분포와 평가 대상·노출·제출·미응답 수 및 비율을 함께 기록한다. 5점 척도·건너뛰기·이용 구간별 1건·최대 30일 보관은 확정이다. 기존 기분·한 줄 소감 입력은 제거한다. 평가값은 GA4로 보내지 않으며 응답자 만족도를 전체 이용자 만족도로 표현하지 않는다.

목표 숫자는 아직 없다. 기준선을 본 다음 실질적으로 의미 있는 최소 개선 폭과 허용할 오류·응답 지연·비용 한도를 **개선 적용 전에** 정한다. 현재 관찰값이나 목표값을 만들어 채우지 않는다.

## 7. 실제 개선 사이클

### 사이클 A — 지금 팀이 하는 UX/UI 개선

근거는 두 명의 과거 시연 관찰과 현재 코드 결함이다. GA4 이전이므로 '전환율이 몇 % 개선됐다'는 주장을 할 수 없다. 디자인안의 핵심 과업을 소수의 실제 대상 사용자에게 수행하게 해 발견성·완료·오류·도움 이유를 확인한다. 과거 화면의 동일 과업 기록이 없으면 수치 전후 비교 대신 문제 재발 여부를 보고한다.

현재 고장이 있는 버전을 장기간 운영하면서 비교군 데이터를 만들지 않는다. 기존 오류를 정상화하고 UX를 적용한 버전을 **정량 기준선 v1**으로 둔다.

### 사이클 B — 배포·GA4 이후 측정 가능한 개선

1. **수집부터 확인:** 일반 보고서·버전·제외 규칙·DB 성공을 대조한다. 갑자기 이벤트가 줄었다면 UX 원인으로 단정하기 전에 태그 오류를 확인한다.
2. **공개·모집·관찰 병행:** 특정 기간이나 참여 인원을 기다리지 않고 확인된 문제부터 개선한다. 자연 유입·직접 모집·진행자 도움을 구분하고 실제 분자·분모·기간을 기록한다. 표본이 부족하면 정량 효과는 판단 보류한다.
3. **원인 후보 선택:** 예를 들어 AI 버튼 클릭은 적지만 발견하면 대부분 대화에 도달하면 발견성, 클릭은 많은데 첫 응답 전에 실패하면 기술 문제, 3턴은 높지만 도움 평가는 낮으면 응답 내용/기대 차이를 우선 조사한다.
4. **개선 1개 선택:** 팀/사용자가 이유와 대안을 검토한다. 버튼 문구와 AI 프롬프트를 동시에 크게 바꾸면 무엇이 작용했는지 알기 어려우므로 한 가설에 필요한 변경만 묶는다.
5. **사전 기록:** 아래 실험 카드의 대상·분모·기간·최소 변화·품질 한도·분석 방식을 고정하고 구현한다.
6. **검증·배포:** 관련 T/Q를 통과시킨 뒤 새 release/UI 버전을 배포한다. 계측 정의가 바뀌면 기존 기준선과 직접 비교하지 않고 다시 수집한다.
7. **재측정:** 같은 과업·유입·기기·모드·모집 조건으로 비교한다. 새 이용자에게 같은 과업을 확인한다. 같은 사람의 재시험은 학습 효과를 분리해 보조 자료로 남긴다.
8. **판정:** 유지·추가 수정·보류 중 하나를 실제 결과로 결정한다. 표본이 작거나 결과가 섞이면 효과를 확정하지 않는다.

| 가설 후보 | 확인해야 할 증거 | 판단을 바꾸는 반대 증거 |
|---|---|---|
| AI 진입 버튼/설명이 불명확해 시작하지 못함 | 사용자에게 버튼 위치·기대 결과를 묻지 않고 과업 수행 관찰; 화면 노출 대비 클릭 | 버튼을 잘 찾지만 AI를 원하지 않는다고 설명하면 발견성만의 문제가 아님 |
| 설정 단계가 길거나 모드 뜻을 오해함 | 모드별 취소 위치·소요 시간·사용자가 예상한 답변 | 설정은 쉽게 마치고 provider 오류로 실패하면 UI 단계 축소보다 안정성 우선 |
| AI 반응이 원하는 도움과 다름 | 상황/공감별 평가·발언·대화 종료 이유 | 만족하고 짧게 종료했다면 3턴 미도달을 실패로 보면 안 됨 |

두 명의 인터뷰는 응답 기대가 다르다는 가설을 지지한다. '모두 무조건적인 편들기를 원한다'거나 '남의 사연에 관심이 없다'는 전체 사용자 결론은 지지하지 않는다.

### 비교 방법과 보고 형식

유입이 충분하면 무작위 A/B를 고려한다. 예상 기준 전환율과 검출할 최소 변화 폭으로 표본 수를 계산한 뒤 시작하며, 임의 인원이나 고정 2주를 통계적 충분성으로 취급하지 않는다. 유입이 적으면 순차 전후 비교 + 과업 관찰을 사용하고 인과관계는 제한적으로 해석한다.

| 항목 | 기준선 v1 | 개선 v2 | 판정에 필요한 설명 |
|---|---|---|---|
| 기간·릴리스·UI·이벤트 정의 | 미수집 | 미수집 | 정의가 다르면 직접 비교 불가 |
| 사용자·유입·기기·모드 분포 | 미수집 | 미수집 | 유입 변화·모집 영향 |
| 관측 첫 방문 세션의 사연 조회 / 첫 정상 답변 도달 / 비율 | 미수집 | 미수집 | 분모·분자 원수 함께 |
| 평가 노출 / 응답 / 긍정·중립·부정 | 미수집 | 미수집 | 응답 선택 편향 |
| 요청 실패 / 응답 시간 / 사용 비용 | 미수집 | 미수집 | 악화되면 안 되는 항목 |
| 관찰된 막힘·사용자 발언 | 미수집 | 미수집 | AI 해석과 실제 발언 분리 |

비율 차이는 **퍼센트포인트**로, 필요하면 상대 변화도 별도 표시한다. n이 작으면 원수와 불확실성을 우선 제시한다. 예상한 차이가 없거나 품질이 나빠졌다면 개선 성공이라고 보고하지 않는다.
